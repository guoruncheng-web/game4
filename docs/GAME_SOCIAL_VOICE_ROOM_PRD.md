# 游戏社交语聊房产品需求文档

> 文档版本：v0.1（产品提案）  
> 日期：2026-09-09  
> 产品范围：`frontend/` PWA + `backend/` 平台与网关  
> 状态：待产品确认，不代表已实现或已批准上线

## 1. 产品决策摘要

将现有“GAME BOX 游戏盒子”升级为“以语聊房为社交入口、以游戏为共同活动”的游戏社交 PWA。

产品不是泛娱乐语音聊天室，也不是把一个麦克风按钮塞进游戏列表。核心体验是：

1. 玩家因某款游戏或共同玩法意图进入小型语聊房。
2. 在房内快速认识、组队、约局或边聊边玩。
3. 一键进入现有游戏，语音关系不断开。
4. 对局结束后回到房间复盘、继续下一局或沉淀为好友。

首发采用“好友 / 邀请制小房间”，暂不开放陌生人公共广场。原因是当前系统已有账号封禁，但还缺少年龄确认、房间级举报、拉黑、主持治理、审计和内容安全闭环。公共语聊房必须在这些能力完成后再开启。

实时音频采用声网 RTC Web SDK 4.x。声网只负责音频媒体传输；房间、角色、麦位、邀请、封禁、举报、游戏关联和 Token 授权由自有后端权威管理。声网 App Certificate 不得进入前端仓库或下发客户端。

## 2. 背景与现状

### 2.1 当前产品

当前 PWA 是移动优先的小游戏合集，首页最大宽度 480px，具备桌面安装、Service Worker 更新、游戏入口、账号、好友和消息能力。当前主导航为“游戏 / 消息 / 我的”。

现有游戏目录包含 10 款游戏，既有单机游戏，也有双人或四人联机、机器人及权威对局。它已经具备“共同活动”，但玩家关系主要停留在好友私信和定向游戏邀请，缺少进入游戏前后的实时陪伴空间。

### 2.2 已有能力盘点

| 已有能力 | 当前实现 | 产品复用方式 | 缺口 |
| --- | --- | --- | --- |
| 登录与身份 | 一键开号、登录、短期 API Token、会话撤销、封禁 | 作为入房唯一身份；继续使用六位 UID | 无年龄确认、无实名或邮箱找回 |
| 头像与资料 | Emoji 兜底、自定义头像、用户名、UID | 房间成员、麦位和邀请统一复用 | 缺少个人签名、常玩游戏、语音状态 |
| 好友系统 | 搜索、申请、同意/拒绝、好友关系 | 好友房邀请、房间可见范围、快速拉人 | 缺少删除好友、拉黑、备注 |
| 私信 | 好友私信、已读、未读、轮询刷新 | 保留为异步关系维护；房间邀请可生成会话卡片 | 尚无房间群聊、消息推送 |
| 在线状态 | 全站登录后 WebSocket 在线列表 | 展示好友是否可邀请；承载房间控制消息 | 当前连接只覆盖既有联机协议 |
| 游戏邀请 | 全站邀请弹窗、接受/拒绝、房间与开局信号 | 改造成统一的“邀请进语聊房 / 邀请一起玩”通知模型 | 当前只适配部分游戏，房间模型不可直接当语聊房使用 |
| 游戏目录 | 上下架、排序、10 款游戏入口 | 房内“玩游戏”入口弹出完整游戏列表 | 缺少语音跨游戏持续连接状态 |
| 钱包 | 平台钻石、交易账本基础 | 首版只展示，不用于购买麦位或发言权 | 暂无消费商品、礼物与结算规则 |
| 客服与管理 | 反馈单、账号封禁/解封、游戏上下架、统计 | 扩展为房间举报、房主处罚、运营监控 | 缺房间审计、举报处置、房间封禁 |
| PWA | 安装、更新提示、离线缓存、全站布局 Provider | 语音连接放在全站 Provider，路由切换时保持 | RTC 本身不能离线；iOS 后台与自动播放需专项验证 |

主要代码依据：

- 首页和现有导航：`frontend/src/app/page.tsx`
- 全站账号、联机与 PWA 容器：`frontend/src/app/layout.tsx`
- 好友与私信：`frontend/src/components/ChatPanel.tsx`
- 在线状态与游戏邀请：`frontend/src/components/CoopProvider.tsx`
- 账号和钱包：`frontend/src/components/AuthProvider.tsx`
- 平台 API：`backend/apps/platform/src/routes.ts`
- 当前数据库：`backend/database/schema.sql`
- 鉴权与服务边界：`backend/docs/architecture.md`

## 3. 产品目标与非目标

### 3.1 产品目标

1. 把“选游戏”从单人浏览行为变成“找人一起玩”的社交行为。
2. 让好友从发消息到一起开玩不超过 3 次主要操作。
3. 让语音在首页、房间和受支持游戏之间持续存在。
4. 用小房间和好友关系降低社交压力，游戏作为房内可选活动而非建房门槛。
5. 在 10,000 分钟测试额度内验证语聊是否显著提高组队和复玩。

### 3.2 非目标

首版不做以下功能：

- 陌生人随机匹配语聊、无限公共大厅或万人房。
- 视频、直播、录音回放、K 歌、背景音乐台或虚拟形象直播。
- 付费上麦、抢麦、抽奖、红包、打赏排行榜或付费礼物。
- 公会、家族、CP、等级特权和复杂主播经济。
- 用声网 RTM 替换现有好友私信和游戏权威 WebSocket。
- 让 RTC 回调推进对局、计分、发牌或持久化状态。
- 在未取得麦克风授权前自动弹权限或自动采集声音。

## 4. 目标玩家与核心需求

### 4.1 目标玩家

| 玩家类型 | 场景 | 核心需求 |
| --- | --- | --- |
| 熟人玩家 | 和已有好友约一局十三张、UMO、捕鱼或 Ludo | 不切到外部聊天 App，边聊边开局 |
| 半熟人玩家 | 由共同好友邀请进房 | 先听、再上麦，低压力认识队友 |
| 单机玩家 | 玩跑酷、水果、台球等游戏 | 有陪伴房可边玩边聊，但不被强迫社交 |
| 房主/组织者 | 固定时间召集朋友 | 快速开房、拉人、控麦、换游戏、开始下一局 |
| 谨慎玩家 | 不愿立即开麦或担心骚扰 | 默认静音、可只听、可退出、拉黑和举报 |

### 4.2 Jobs to be Done

- 当我想玩一局但不想一个人玩时，我能快速找到在线好友并先进入同一个语聊空间。
- 当大家还没决定玩什么时，我们能在房里看到可玩的游戏并共同选择。
- 当游戏开始时，我不需要退出语音、复制房号或反复切应用。
- 当有人打扰或辱骂时，我能立即静音、拉黑、举报并离开，而不是只能忍受。
- 当网络或页面刷新时，我能知道语音处于重连、仅收听或已断开的哪一种状态。

## 5. 产品定位与体验原则

### 5.1 一句话定位

“和朋友边聊边玩的轻量游戏房。”

### 5.2 产品支柱

1. **语聊先成立，游戏按需进入**：创建房间不要求选择游戏；玩家在房内打开游戏列表，随时选择游戏并保持语音关系。
2. **小房间先于大广场**：首版至少 8 个麦位；房间成员上限与扩展麦位数另行配置和压测，控制噪音、成本与治理复杂度。
3. **先听后说**：进入房间默认只听且静音，用户主动申请或点击空麦位后才请求麦克风权限。
4. **关系可沉淀**：房内可添加好友、私信和再次邀请，语音不是一次性连接。
5. **权威可治理**：房主和服务端决定麦位与成员状态，客户端展示不能等同于授权。

### 5.3 设计框架

- MDA 的目标体验为 Fellowship（陪伴与合作）和 Discovery（发现新队友/新游戏）。
- SDT 对应关系：自主性来自可选游戏、可只听或上麦；胜任感来自顺畅组队与对局；关系感来自语聊、好友和重复开房。
- Flow 要求语聊不打断游戏操作。语音控件在游戏中收拢成迷你条，只保留静音、成员数和返回房间。

## 6. 核心循环

### 6.1 30 秒循环

看见房间或好友在线 → 进入并听到声音 → 打招呼/回应 → 决定留下、上麦或打开游戏列表。

### 6.2 5 分钟循环

召集好友 → 占麦交流 → 选择游戏/模式 → 发起一起玩 → 全员确认 → 进入游戏。

### 6.3 单次会话循环（15—45 分钟）

进房暖场 → 一至多局游戏 → 房内复盘/换游戏 → 添加好友或约下次 → 主动离房。

### 6.4 长期循环

好友关系增加 → 常用房和常玩组合形成 → 更容易组织下一局 → 社交留存和游戏复玩提高。

## 7. 信息架构

### 7.1 主导航调整

现有三栏调整为四栏：

| 导航 | 目的 | 默认内容 |
| --- | --- | --- |
| 房间 | 新的默认首页和主增长入口 | 好友正在聊、最近房间、创建房间 |
| 游戏 | 保留全部游戏入口 | 继续玩、联机游戏、单机游戏 |
| 消息 | 私信、好友申请、房间邀请记录 | 未读聚合 |
| 我的 | 资料、语音设置、账号、安全与客服 | 当前资料和钱包 |

首次上线可对老用户保留“游戏”为默认页 7 天，并用一次性引导介绍“房间”；新用户默认进入“房间”。该开关必须可配置和回滚。

### 7.2 页面流

```text
登录/注册
   └─ 房间首页
      ├─ 创建房间 ─ 房名/可见性 ───── 房间
      ├─ 好友房间 ────────────────── 房间
      └─ 邀请通知 ─ 接受 ─────────── 房间

房间
   ├─ 上麦/下麦/静音/邀请/房间文字聊天
   ├─ 一起玩 ─ 游戏确认 ─ 游戏路由 + 迷你语音条
   ├─ 查看成员 ─ 加好友/私信/静音/举报/移出
   └─ 离开房间 ─ 返回原页面
```

## 8. 房间模型

### 8.1 房间类型

| 类型 | 谁可发现 | 谁可加入 | MVP |
| --- | --- | --- | --- |
| 好友房 | 房主及成员的好友 | 好友直接加入或受邀加入 | P0 |
| 私密房 | 不出现在列表 | 使用一次性邀请链接/房间码 | P0 |
| 公共主题房 | 全体已登录用户 | 满足安全条件后直接加入 | P1，受治理门禁阻断 |

### 8.2 容量与角色

- 每房至少提供 8 个麦位，首屏使用 2×4 布局；房间成员上限不在本版本写死，必须高于或等于麦位数并由服务端配置。
- 角色：房主、协管、麦上成员、听众。
- 房主拥有换主题、邀请、批准上麦、抱下麦、静音成员、移出成员、转让房主和关闭房间权限。
- 协管仅拥有批准上麦、静音和移出权限，不能关闭房间或转让房主。
- 成员可静音自己、申请上麦、下麦、邀请好友、发房间文字消息、举报和离开。
- 服务端保存权威角色与麦位；声网发布音频权限必须由服务端签发的 Token 对应。

### 8.3 房间生命周期

```text
CREATING → OPEN → PLAYING → OPEN → CLOSING → CLOSED
                 └───────────────┘
```

- `CREATING`：服务端创建权威房间并返回房间 ID。
- `OPEN`：允许入房、上麦和选择游戏。
- `PLAYING`：成员可从房内游戏列表进入游戏，语聊继续；仍允许受邀好友进入。
- `CLOSING`：房主关闭或最后一人离开，拒绝新 Token。
- `CLOSED`：RTC 成员全部退出，临时邀请失效，房间消息只保留安全所需时长。

房主异常断线后保留 60 秒；超时按“协管 → 最早麦上成员 → 最早在房成员”的顺序转让。空房立即关闭。所有时长均为后端可配置参数。

### 8.4 游戏关联

- 创建语聊房时不选择游戏，房间可独立进行语音与文字聊天。
- 房内提供固定“玩游戏”入口，点击后弹出当前可用的完整游戏列表；选择游戏后进入对应路由。
- 房间可选记录一个当前活动游戏，用于成员提示；该字段可为空，也不限制其他成员选择不同游戏。
- 所有 10 款游戏均可作为房间主题和个人跳转入口。
- “同步开局”仅对已经完成多人协议适配和验收的游戏开放，不能仅凭游戏卡片存在就显示可用。
- 首轮重点验证十三张、UMO、捕鱼、Ludo；具体上线名单由运行验收决定。
- 单机游戏使用“各自游玩、保持语聊”模式，不伪造多人同步状态。
- 语聊不读取其他玩家私有手牌，也不成为游戏权威状态来源。

## 9. 关键页面与交互

### 9.1 房间首页

信息优先级：

1. 好友正在参与的房间及“立即加入”。
2. “创建房间”主按钮。
3. 最近加入过的房间与在线好友。
4. 游戏推荐作为次级入口。

空状态不能只写“暂无房间”，应提供“邀请在线好友开一间”和“先去选游戏”两个动作。

### 9.2 创建房间

必填：房间名称（默认“{用户名} 的语聊房”）、可见性。创建阶段不展示游戏选择。  
选填：6 位房间码、进入是否默认只听、是否需房主批准上麦。

创建成功后房主先进入房间，RTC 尚未连接时显示“正在连接语音”，不能用空麦位画面掩盖连接失败。

### 9.3 房间主界面

```text
┌ 返回  房间名 / 网络状态      ··· ┐
│ [玩游戏] 点击弹出完整游戏列表       │
│                                  │
│ [房主麦] [麦位2] [麦位3] [麦位4] │
│ [麦位5] [麦位6] [麦位7] [麦位8]  │
│ 头像/昵称/说话波纹/静音图标       │
│                                  │
│ 房间消息与系统事件                │
│                                  │
│ [邀请] [文字] [静音/开麦] [离开] │
└──────────────────────────────────┘
```

- 首屏必须同时回答：我在哪个房、谁在说、我是否开麦、当前玩什么、怎么离开。
- 说话状态同时使用头像外圈动画、麦克风图标和文字可访问名称，不能只靠颜色或波形。
- 自己的静音按钮固定在底部拇指区；“离开”与“静音”不可紧邻且同色。
- 点空麦位才触发麦克风权限；拒绝后仍以听众留在房内，并提供去系统设置的说明。
- 切到游戏后显示可折叠迷你语音条：说话者头像、静音、房间人数、返回房间。

### 9.4 邀请

- 复用现有全站邀请弹层的交互模式，但区分“进语聊房”和“一起玩游戏”。
- 邀请卡显示邀请人、房间名、当前人数与麦位数；存在当前活动游戏时作为次级信息显示。
- 接受前不申请麦克风权限；接受后默认静音/只听。
- 同一邀请可幂等处理；过期、房间关闭或被移出后需给出明确结果。

### 9.5 房间文字消息

- 作为语音不可用、听障参与、链接分享和系统通知的备用渠道。
- 首版限制 1—500 字，沿用私信限流思想，但数据表和权限必须与私信分离。
- 系统消息包括加入、离开、上麦、下麦、游戏切换、房主转让和处罚。
- 不在 RTC 数据流内承载权威消息；由自有网关发送和持久化。

### 9.6 我的 / 语音设置

新增：

- 默认入房静音（默认开启）。
- 输入设备选择（浏览器支持时）。
- 语音音量与游戏音量分别控制。
- 自动压低游戏背景音乐（默认开启，仅降低 BGM，不降低关键游戏提示音）。
- 按住说话模式。
- 弱网时仅音频低码率模式。
- 已拉黑用户与举报记录入口。

现有 `game-box-muted` 是游戏音效总开关，不得直接控制语聊。语聊必须使用独立持久化键和独立音量状态，避免玩家为了听队友被迫开启游戏音效。

## 10. 新手引导与返回体验

### 10.1 首次 3 分钟

1. 登录后看到“创建好友语聊房”及一名在线好友。
2. 创建房间时只要求房间名称和可见性，不要求选择游戏。
3. 进入后先听，不立刻请求麦克风权限。
4. 点麦位时用单屏解释“仅在房间内使用麦克风”，随后触发浏览器权限。
5. 成功上麦后立即显示自己的说话指示和静音状态。
6. 邀请好友后能看到发送、接受、进入三个明确状态。

### 10.2 返回和恢复

- 7 天未使用语聊：再次入房展示一次“默认静音、随时离开”的轻提示。
- 路由切换：保持 RTC 会话，不重复请求权限。
- 页面刷新：通过有效平台登录和房间成员资格重新取 Token；恢复为静音，不自动恢复发流。
- 网络中断：显示“重连中”，保留静音意图；恢复后重新校验麦位，不相信客户端旧状态。
- 账号登出、改密、封禁或 Token 撤销：关闭 RTC、本地音轨和控制连接，旧声网 Token 不得继续用于重新入房。

## 11. 声网 RTC 接入规格

### 11.1 技术边界

声网 Web SDK 4.x 通过 npm 集成到前端，仅采集与播放音频。生产环境已经使用 HTTPS，满足 Web 麦克风能力的基本条件。

推荐控制流：

```text
PWA ──登录凭证──> Gateway ──内部身份──> Voice Service
PWA <─房间状态/RTC Token─────────────── Voice Service
PWA ══加密音频媒体流══════════════════> 声网 RTC
```

- 新建 `backend/apps/voice`，使用官方 Nest CLI 生成并分配独立内部 HMAC 密钥与端口。
- 网关仍是唯一公开业务入口，负责每次 HTTP、WebSocket 握手和命令的登录有效期/撤销检查。
- platform 保持账号、好友、钱包、举报和账号级处罚的持久化职责。
- voice 负责房间、成员、麦位、房主转让、RTC Channel 映射和短期 Token 签发。
- App ID 可作为客户端配置下发；App Certificate 只存在后端私密环境。
- 使用 AccessToken2，频道名、RTC UID、加入权限和发布音频权限均由服务端绑定。
- 听众 Token 不带发布音频权限；上麦成功后由服务端重新签发具备发布权限的短期 Token。
- Token 建议 15 分钟有效，SDK 提前过期事件触发续签。具体时长为服务端配置项。
- 频道名使用不可猜测的内部 ID，不使用房间标题、用户名或六位展示 UID。

官方依据：

- [Web SDK 4.x API](https://doc.shengwang.cn/api-ref/rtc/javascript/overview)
- [AccessToken2 与发布权限控制](https://doc.shengwang.cn/doc/rtc/javascript/basic-features/token-authentication)

### 11.2 PWA 与浏览器约束

- 只在明确用户手势后创建本地麦克风轨道。
- iOS Safari/PWA 必须验证音频自动播放恢复、锁屏、切后台、蓝牙耳机和来电中断。
- 游戏、系统提示音和远端语音需分通道管理，防止爆音和互相遮盖。
- 页面卸载、登出、离房和被踢时必须停止并关闭本地音轨。
- Service Worker 不得缓存 RTC Token、房间成员响应或任何带凭据接口。
- SDK 升级需固定版本并跑浏览器兼容回归，不能使用浮动版本直接发布。

### 11.3 额度规划

声网分钟按用户在 RTC 频道内的时长累计，而不是只按“房间存在时间”计算。10,000 用户分钟约等于 166.7 用户小时；平均 4 人同时在房时约为 41.7 房间小时。

内测按 80% 预算使用，保留 20% 故障重试和专项测试余量：

- 可用测试预算：8,000 用户分钟。
- 等价于约 133 场“4 人 × 15 分钟”的完整房间测试。
- 或 100 名测试者每人 5 次、每次 12 分钟，共 6,000 用户分钟，余量 4,000 分钟。
- 控制台和自有监控设置 50% / 75% / 90% 告警。
- 内测环境达到 90% 后停止创建新测试房，但不强退进行中的房间。

正式计费与免费额度以声网控制台、账号合同和当期官方计费规则为准。

## 13. 安全、隐私与治理

### 13.1 P0 必须具备

- 仅登录用户可入房，好友房和私密房默认不可被陌生人发现。
- 单用户静音、拉黑、举报、离房；房主静音、下麦、移出、关闭房间。
- 被拉黑双方不可互相邀请，且默认不进入同一好友房。
- 被封禁、登出、改密或撤销会话后，控制连接立即失效，Voice Service 拒绝续签 RTC Token。
- 举报分类至少包含骚扰辱骂、仇恨歧视、色情、未成年人安全、诈骗引流、冒充和其他。
- 管理后台能查看房间元数据、成员事件和举报，不展示或保存原始音频。
- 房间关闭、被踢和 Token 过期均执行幂等清理。

### 13.2 公共房上线门禁

以下条件全部满足后才可开放公共主题房：

1. 年龄确认与未成年人保护策略已确定。
2. 举报、拉黑、房间封禁、账号处罚和申诉闭环已通过验收。
3. 运营后台支持活跃房、异常频率、举报队列和处置时限。
4. 房间文字通道和语音信息有等价的无障碍参与方案。
5. 隐私政策、麦克风用途说明、数据保留与第三方 SDK 披露完成。
6. 至少完成一次真实用户安全演练和一次管理员处置演练。

## 14. 无障碍与包容性要求

- 所有语音状态必须同时有文字/图标反馈，不能只靠音量波形或颜色。
- 全流程支持触屏、键盘和屏幕阅读器；按钮暴露名称、角色、按下状态与禁用原因。
- 房间必须有文字通道，确保不能或不愿开麦的玩家可参与。
- 提供按住说话、默认静音、单独静音某成员、独立语音音量和减少动态效果。
- 字号跟随系统缩放，关键按钮触控面积至少 44×44 CSS px。
- 麦克风授权失败不能阻断入房、阅读消息、邀请或进入游戏。
- 公共发布前评估实时字幕方案；未提供字幕时不得宣称语音功能达到完整听障无障碍。

## 19. 发布与回滚

- 第一阶段仅内测账号可见“房间”，通过服务端开关控制。

- RTC 故障时降级为房间文字消息和普通游戏入口，不能阻断现有游戏。
- Voice Service、PWA、Service Worker 和声网配置作为一个发布单元验收。
- 首次修改或发布到 game4 前，必须重新完整执行 `studio/GAME4_PWA_DEPLOYMENT_PLAYBOOK.md`。
- 回滚需关闭创建房间和 Token 签发，允许现有房在短期内自然结束，再移除前端入口。

## 20. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 公共语音内容安全 | 高 | P0 仅好友/邀请制；治理门禁完成后才开放公共房 |

## 22. 产品成功判定

当邀请制内测同时满足以下条件，才进入公共房设计：

- 技术指标达到第 15.4 节目标，且没有越权发流或账号撤销失效问题。
- 至少 25% 的有效语聊房促成共同进入游戏。
- 多数测试者认为语聊让“约人开局”更容易，而不是只增加入口复杂度。
