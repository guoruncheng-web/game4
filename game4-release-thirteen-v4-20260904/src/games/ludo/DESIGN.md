# Ludo 产品设计

> 分两半：**§A 房间**（开局之前的一切）和 **§B 棋局**（规则与玩法）。
> 两半都按 `image/` 下的新版 Ludo 概念图定；规则内核已实现，25 项用例覆盖（`pnpm ludo:test`）。

## 1. 产品定位

- **类型**：4 人回合制棋盘竞速 / 支持单人对机器人、朋友开房、机器人补位。
- **平台**：手机**竖屏**浏览器为主（**720×1280 逻辑分辨率**）。房间页是 DOM，棋盘是 Three.js。
- **五个页面**：加载 → 大厅 → 房间 → 开局动画 → 对局（见 §2）。
  点首页卡片进的是**加载页**，棋盘只在房主点「开始」并放完开局动画之后才挂载。
- **目标时长**：房主设定（5 / 10 / 15 分钟），到点按分数排名。
- **核心体验**：房间里的**社交前戏** + 棋局里的**掷二选一**。
  这类游戏有一半乐趣发生在开局之前——等人、催人、加机器人、把游戏 ID 发到聊天框。
- **在游戏盒子里的定位**：盒里现有 8 款全是自己跟自己较劲。这是**第一款「约人一起玩」的游戏**，
  也是第一款需要「房间」这个概念的游戏。
- **设计边界**：不做语音（参考图里麦克风就是禁用态）、不做礼物/付费、不做房间列表大厅、不做观战。

# §A 房间

## 2. 具体流程（五个页面）

**这一节是产品定义的主干，其余各节都是它的细节。** 概念图在 `image/` 下，文件名标在每一步后面。

```
点卡片 → ① 加载页 → ② 游戏大厅 → ③ 游戏房间 → ④ 开局动画 → ⑤ 对局
                         ↑                ↓
                         └──── 离开 ──────┘
```

### ① 加载页

点首页卡片后**先进加载页**，不是直接进大厅。

- 中央 logo + 进度条，加载完自动进大厅，不需要点。
- 这一页存在的理由是**把 3D 棋子模型、贴图、音效的下载摊在这里**。
  没有它，玩家会在大厅点了「创建房间」之后才开始等，而那时候他已经在等人了——两段等待叠在一起最难受。
- 加载失败要明说（「资源加载失败，点此重试」），不能停在 99% 装作还在加载。

### ② 游戏大厅　`image/room-entry-concept-v4.png`

- 顶部：**大厅标题** + 当前在大厅里的用户
- 中央：**游戏 logo**
- 中下部两个主按钮：**[创建新游戏房间]** / **[加入已有游戏房间]**
  - 创建 → 生成房间，自己即房主，弹窗给出房间 ID（`image/create-game-success-concept-v3.png`）→ 进 ③
  - 加入 → 弹窗输入 6 位房间 ID（`image/join-existing-game-concept-v3.png`）→ 进 ③
- 底部聊天区：历史消息列表 + 消息输入框 + **[发送]**，三个部分必须同时可见。

**大厅不列房间列表。** 房间靠 ID 邀请熟人（理由见 §2.1），列表只会带来陌生人中途退出的问题。

### ③ 游戏房间　`image/pre-game-host-concept-v2.png`

- 顶部：**默认房间名** + **房间 ID**（可复制）+ 房间里的用户
- 中央：**游戏 logo**；**房主视角多一行时长调节**（`◀ ⏰ 05:00 ▶`），其他人只能看
- **四个槽位**：第一个是房主，其余空槽显示 **＋**
  - **进房 ≠ 入座**：进到房间里的用户点 **＋** 才算加入这一局。
    这样房间可以容纳超过 4 个人（后来的人先待着，有人离座就能补上），
    也避免了「进错房间就白占一个位子」。
  - 房主可以把非房主移出座位（槽位上的 ✕）
- 底部按钮：
  - **房主**：`离开` + `准备`；自己准备好之后，`准备` 变成 **`开始`**（其他人未齐时置灰）
  - **其他人**：`离开` + `准备`；已准备则显示 `已准备`（不可再点，可取消）

### ④ 开局动画　`image/game-start-animation-concept-v2.png`

房主点「开始」之后**不直接进棋盘**，先播一段开局动画：四家依次亮相 + 棋子入场。

- 时长 2~3 秒，**不可跳过**。
- 它不是装饰，是**告诉所有人「谁是哪一色、坐哪个方位」**——
  四人局如果一上来就是满屏棋子，前两个回合都会有人搞不清自己是哪一家。

### ⑤ 对局　`image/gameplay-concept-v2.png`

见 §10.3 的版式。对局结束后回到 ③ 房间页，成员和房间 ID 都保留，可以直接再来一局。

## 2.1 为什么房间靠 ID 而不是房间列表

捕鱼用的是开放房列表（谁都能补座、随进随打），这里**不能照抄**，两条理由：

1. **回合制必须等齐人。** 捕鱼少一个人只是少一张网；这里缺人就开不了局，
   必须有「准备 → 全员就绪 → 房主开始」这个闭环。
2. **它是约人玩的游戏，不是碰运气凑人的游戏。** 陌生人凑局最大的问题是有人打到一半跑掉，
   剩下三个人的十几分钟作废。**靠房间 ID 邀请熟人**才是这个品类的正常形态。

```
│    👤        👤                      │  空槽点一下入座

│                                      │

├──────────────────────────────────────┤
│  小明 进入了房间              12:24  │  聊天流(系统消息 + 玩家发言)

│  [ 聊一聊～                  ] [发送] │
└──────────────────────────────────────┘
```

## 4. 房间 ID

- **6 位数字**。不用字母：要能在语音里念出来、能用数字键盘直接敲。
- 创建成功后**弹窗展示 + 一键复制**，并且**自动往聊天流里发一条可点复制的记录** ——
  弹窗关掉之后 ID 就找不回来，是这一页最容易发生的挫败。
- 聊天里出现的 6 位数字**自动识别成可点击的 ID**（点一下就复制）。
- ID 在房间销毁后**冷却 10 分钟**才回收，避免刚散场就有人误入同号新房。

## 5. 成员位与状态

| 元素 | 规则 |
| --- | --- |
| 顺序 | **第一个恒为房主**，头像左上角挂徽章，其余按加入顺序 |
| 准备态 | **所有人都要点准备**（含房主），头像下方显示 `✓ 已准备` / `● 未准备` |
| 踢人 | 只有房主能踢，非房主头像右上角红 ✕；被踢者 60 秒内不能用同一 ID 回来 |
| 机器人 | 统一图标，**恒为已准备**；房主可随时移除 |
| 空位 | 显示 ＋，房主点它 = 加机器人（和下方按钮同一个动作，只是更好点） |

**按钮两态**（参考图 122646 与 122634 正是这两态）：未全员准备时房主看到**灰色**的「开始」，
齐了才变绿；非房主始终是「准备 / 取消准备」。

**开始条件**：`所有真人都已准备` 且 `人数 ≥ 2`。不足 4 人也能开——**缺的位子在开局瞬间自动补机器人**。
硬性要求「必须 4 个真人」会让绝大多数房间永远开不了局。

**房主离开**：房主转给第一个真人；房里只剩机器人则销毁房间。

## 6. 局时长与三道保险

房主用 `◀ ⏰ 05:00 ▶` 在 **5 / 10 / 15 分钟**之间切，默认 5 分钟。
非房主看得见、点不动（点了给提示，不要装作没反应）。

| 保险 | 管的是什么 |
| --- | --- |
| 赛道长度（52 格 / 4 颗） | 正常打完大概要多久 |
| **局时长**（房主设） | 有人磨蹭时的硬性上限 |
| **回合上限 150 回合** | 所有人都磨蹭时的兜底 |

任意一道触发就结算，按分数排名。**不要再加第四套收尾规则**——多套并行会让玩家永远搞不清
这局什么时候结束。

> **参考图上写的是 `Round: 1/50`，照抄会出事。** 本作每家 4 颗 × 62 步 = 248 步，
> 50 回合每家只有 50 次移动、每次最多 6 步，**理论极限都跑不完** ——
> 于是「四颗全到家者胜」这个胜利条件永远触发不到，每局都撞回合墙结束。
> 无头对局验证过：50 上限时 200 回合结束、0 人到家；提到 150 之后，12 局里 12 局有人真的跑完。
>
> 分工因此明确：**局时长是主控**，回合上限只防「所有人一起磨蹭」这种极端情况。
> 也就是说 5 分钟局的**常态结局是时间到 + 按分数排名**，这和参考图把分数放在正中间是一致的。

## 7. 聊天

- **只做文字**。语音在这个体量下不划算：权限、回声、噪声、举报都要处理。
- 三类消息：**系统**（`小明 进入了房间`）、**玩家**（`小明：等我一下`）、**可复制房间 ID**。
- 服务端只转发不解析，但要做三件事：**限长 200 字**、**限频 1 秒 1 条**、**去掉换行**。
  不做敏感词过滤——这个体量做不好，而且房间是靠 ID 邀请的熟人局。
- 聊天记录**不落库**，随房间销毁。

## 8. 服务端

复用 `server/ws.mjs` 现有的房间与连接层，按 `game === 'ludo'` 挂一个适配器（照 `server/fish-room.mjs`）。

| 能力 | 现状 | 要做的 |
| --- | --- | --- |
| 4 座房间 | ✅ 捕鱼已有 | 复用 |
| 房间号 | ❌ 自增整数 | 6 位随机数 + 10 分钟冷却回收 |
| 准备态 / 踢人 / 机器人 / 聊天 / 房主设置 | ❌ | 新增消息 |

**房间属于这一款，不做「房间里换游戏」。** 一间房能换游戏意味着房间要独立于任何游戏存在，
准备态、机器人、开始条件全得做成可插拔的，而现在只有一个使用者。
**为一个不存在的第二使用者做抽象，是这个体量下最常见的浪费。**
代码放 `server/room.mjs`、和回合逻辑分开写就够了，真有第二款要用时再抽。

三条本款特有的约束：

1. **骰子必须服务端摇。** 客户端摇 = 自己填分数，是唯一的作弊入口。
2. **回合限时 30 秒**，超时自动走最保守的合法走法。
   最怕的不是有人退出，是有人挂着不走，四个人一起卡死。
3. **掉线补机器人**：真人掉线，棋子交给「老手」AI 接管，局照常打完。

# §B 棋局

## 9. 标准 Ludo 不能照搬

规则是标准 Ludo，但有四处刻意的改动。每一处都对着一个具体的体验问题。

### 9.1 开局可能十几轮什么都做不了

标准规则必须掷 6 才能出子，单骰掷不出 6 的概率 5/6，**连续四轮出不了子的概率高达 48%**。

> **改法**：掷 **5 或 6** 都能出子；**开局每人先有一颗在入场格上**。第一回合所有人都有得走。

### 9.2 大量回合根本没有选择

掷出点数后很多局面只有一种合法走法。**没有选择的回合不是游戏，是等待。**
Ludo 被诟病「纯运气」的根源就在这里。

> **改法（全篇最重要的一条）**：**每回合掷 2 个骰子，只能用 1 个**，另一个作废。
> 已用无头对局验证：合法走法数中位数 **6**，无路可走的回合占比 **0.3%**。
> 你仍然不知道会掷出什么，但**掷出来之后怎么用是你的事**。

### 9.3 结尾拖沓

标准规则进终点要精确点数，最后几分钟常常在等某个人掷出那一个数。

> **改法**：**点数 ≥ 所需即可进终点**，不用精确。再加 §6 的三道时长保险。

### 9.4 被撞之后容易躺平

撞子回基地是 Ludo 唯一的对抗手段，**不能削弱**——试过改成「退回最近的安全格」，
结果是这游戏仅有的互动也变得无关痛痒。但挨撞的人如果觉得这局已经废了，
剩下十几分钟四个人里就有一个在敷衍。

> **改法**：撞子照旧回基地，但**被撞方下一回合掷 3 个骰子选 1**。
> 挨打之后立刻拿到更强的选择权，比「少退几格」有用得多。

### 9.5 改动全表

| 标准 Ludo | 本作 | 为什么 |
| --- | --- | --- |
| 掷 6 出子 | 掷 5 或 6，且开局送一颗在场 | §9.1 |
| 掷 1 个骰子 | **掷 2 个，用 1 个** | §9.2 |
| 进终点要精确点数 | 点数够就行 | §9.3 |
| 撞子回基地 | **不变**，但被撞方下回合掷 3 选 1 | §9.4 |
| 掷 6 再掷一次 | **不做** | 已被「掷二选一」替代；两套叠加会让单回合失控 |
| 4 颗 / 52 格 | **不变** | 玩家的肌肉记忆，时长交给 §6 的三道保险 |

## 10. 棋盘与规则

### 10.1 棋盘

外圈 **56 格**（四臂各 14 格），四个基地各 4 颗棋子，四条终点道各 6 格。
一颗棋子从入场到到家共 **62 步**。

> **为什么是 56 而不是常说的 52**：标准 Ludo 盘是 15×15 的十字——竖条占第 6/7/8 列、
> 横条占第 6/7/8 行、中心 3×3 是终点区、四条终点道各 6 格。**在这个几何下外圈恰好 56 格**，
> 且每格正好两个邻居，是一个完美的简单环。想凑成 52 只能挖掉中心块的四个内角格，
> 那样环会断开（8 个格子变成死胡同）。
>
> 这个数**不影响任何规则**，只决定跑一圈多远。取几何算出来的那个数，是为了让**渲染和规则用同一套坐标**——
> 对不上的话棋子会走到格子外面去，而这种错在画面上极难查。见 `sim/layout.ts`。

**外圈格子本身没有任何特殊效果**——没有捷径、没有跳跃格。落点永远是「当前步数 + 点数」。
这是 Ludo 的地基：别往里加「踩到某格前进 N 步」之类的规则，那会让整盘的距离计算失去意义。

**安全格 8 个**：四个彩色入场格 + 四个 ★（各自入场格往前第 8 格）。站在上面撞不动。

**座位顺序就是环上顺序**（0 红下 → 1 绿左 → 2 黄上 → 3 蓝右）。
一开始按「红黄蓝绿」排，结果轮次会在棋盘上**跨对角跳**，四个人都搞不清下一个该谁。

棋盘分两层：`sim/board.ts` 是规则用的数据表（入场格、安全格），
`sim/layout.ts` 是几何（15×15 网格坐标、环路、终点道、基地槽位）。
**渲染只读 layout，规则只读 board**，两边共用 `config.TRACK` 这一个数，自检会盯着它们对不对得上。

### 10.2 胜负与计分

四颗全到家者胜，产生完整名次。三道保险任意一道触发都会结算。

```
一颗的分 = 到家 100 分，否则 floor(已走步数 / 58 × 100)
一家的分 = 四颗之和，满分 400
```

有了分数，「时间到」的结算才有明确依据——光按「谁到家的多」会出现大量并列，
而并列在四人局里是最扫兴的结果。

### 10.3 棋盘页布局

按参考图 `20260820-122627.png`，**房间的顶栏和聊天流在对局中一直在**——
桌游的乐趣有一半在下棋时的互相调侃，把聊天藏起来等于把这一半关掉。

```
┌──────────────────────────────────────┐
│ Ludo   房间号 972341             [⋯] │  顶栏常驻
│  ⏰ 04:56      Round 1/50      [⚙]   │  三道保险里的两道摆在这
├──────────────────────────────────────┤
│ ┌────────┬─────┬────────┐           │
│ │ 👤绿家 │  ↓  │👤黄家   │           │  四角 = 四家:头像 + 分数 + 基地
│ │   0    │     │   0    │           │
│ ├────────┼─────┼────────┤           │
│ │        │ ╱╲  │        │           │  中央十字 = 四条终点道
│ ├────────┼─────┼────────┤           │
│ │   0    │     │   0    │           │
│ │ 👤我 🎲│  ↑  │👤蓝家   │           │  轮到谁,该家区块亮起 + 骰子可点
│ └────────┴─────┴────────┘           │
├──────────────────────────────────────┤
│  小明：这把稳了                       │  聊天流常驻
│  [ 聊一聊～                  ] [发送] │
└──────────────────────────────────────┘
```

- **自己永远在左下角**：本地把座位号映射一次，别人依次顺时针排。
  和捕鱼那边「上排座位转相机」是同一个道理——玩家不该对着别人的视角玩。
- **轮到谁**：该家区块整体亮起 + 指向箭头，骰子按钮只在自己回合可点。
- 棋盘上标出 ★ 安全格和行进方向箭头。

## 11. 单人与机器人

**必须有单人**：凑不齐人是常态。单人 = 你 + 3 个机器人，房间页「创建游戏 → 加满机器人 → 开始」。

三档难度，**区别在评估函数权重，不在掷骰子作弊**：

| 档 | 行为 |
| --- | --- |
| 新手 | 只挑点数大的走，不主动撞、不避险 |
| 老手 | 能撞就撞，优先把领先的棋子送进终点道 |
| 老江湖 | 额外计算「走完这步我会不会落在别人射程里」，宁可少走也要站安全格 |

**机器人绝不作弊。** 玩家对电脑作弊的嗅觉极其敏锐，一旦怀疑，输了不服气、赢了也不高兴。
思考时间固定 0.6~1.2 秒随机：秒回像没在想，太慢让人等。

## 12. 视听方向（细则交给 game_artist 写 ART.md）

- **房间页是 DOM**，深蓝渐变底 + 大圆角卡片，亮色大按钮（离开=暖黄，准备=紫，开始=绿）。
- **棋盘按参考图做成清晰的 2D 俯视十字盘**，但**棋子用 3D 模型 + 正交俯视相机渲染** ——
  参考图里的棋子本身就是 3D 渲染的。一份棋子模型四色染色（`accent` 材质，和捕鱼炮台同一做法）。
- **「撞」是这游戏唯一的对抗瞬间**：撞击时顿帧 80ms，被撞的棋子翻滚回基地。顿帧决定这一下有没有分量。
- 骰子 3D 真滚，但**结果是服务端定的**，客户端按结果反推轨迹。
- 音效走 rFXGen：掷骰、落子、撞击、进终点道、到家、胜利、进房提示。

## 15. 验收

**房间**
- 创建 → 弹窗给出 6 位 ID → 关掉弹窗后，聊天流里仍能找到并复制这个 ID。
- 两台设备用同一 ID 进同一间房；输错 ID 给明确提示而不是静默失败。
- 房主踢人：被踢者立刻回到「创建/加入」态，60 秒内不能用同一 ID 回来。
- 全员准备 → 房主按钮才从灰变亮；有人取消准备 → 立刻变回灰。
- 房主离开 → 转给第一个真人，房间不解散。
- 聊天连发 10 条：被限频挡下的有明确反馈，不是静默丢弃。
- 只有 2 个真人时点开始 → 自动补 2 个机器人，开局是 4 家。

**棋局**
- 同一局面 + 同一点数，`legalMoves` 输出逐条可复现。✅
- 棋盘自检：8 个安全格、四家入场格等距、一颗棋子走 62 步。✅
- 几何自检：环路 56 格且每格两个邻居、**整条路径每一步都走到相邻格**（含拐进终点道那一下）、
  基地格不和外圈/终点道重叠、座位顺序就是环上顺序。✅
- 每回合合法走法数中位数 ≥ 2。✅ 实测 6。
- 开局任意点数下四个人都至少有一种走法。✅
- 4 人局（3 机器人）中位时长落在设定时长的 ±20% 内。
- **胜利条件够得着**：给足时间的无头对局里，绝大多数局有人真的把四颗全送到家，
  而不是每局都撞回合墙。✅ 12/12
- 同一个随机种子必须复现同一整局（服务端出问题时能重放）。✅
- 同一回合重复摇骰不会换点数。✅
- 改掉客户端的骰子结果，服务端必须拒绝这一步。
- 一个人中途关页面，剩下三人正常打完，棋子由机器人接管。
