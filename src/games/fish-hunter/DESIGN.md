# 深海捕鱼（fish-hunter）—— 多人联机设计

slug `fish-hunter` · 引擎 Phaser 3 · **横屏 1280×800** · 最多 4 人同池 · 服务端权威

---

## 0. 目标与非目标

**目标**

- 一个房间最多 4 人，**共享同一片鱼池**：谁都能打同一条鱼，谁打死算谁的。
- 金币是**跨局持久**的账户余额（存 Postgres），开炮扣钱、捕获给钱。
- 一个人也能玩：不登录、断网也能开局，跑的是同一份模拟代码。
- 中途进出自由：有人退出不影响别人，空座位随时能被补上。

**非目标（v1 明确不做）**

- **明确不做充值**，不做任何真实货币入口、也不预留入口（不留「商店」按钮、不留 IAP 字段、不留价格表）。金币只能靠打鱼和破产补助获得（见 §6.4）。这是一条硬约束，不是 v1 的临时取舍——它同时决定了 §6.3 的 RTP 该怎么定（没有付费回血，就不能靠掏空玩家来制造压力）。
- 不做排行榜/公会/赛季。先把「一池鱼四个人打」这件事做对。
- 不做观战、不做回放。
- 不做竖屏适配。这一款是横屏（§4.3），竖屏时只显示一张「请横屏」引导页，不做两套布局。

## 1. 为什么不能沿用霓虹突击那套联机

霓虹突击 2D 的联机是：2 人房，服务端只转发不解析，host 的浏览器裁决一切（`server/ws.mjs` 的 `case 'game'` + `coop/protocol.ts`）。那套方案对它是对的——**双人协作、分数各记各的、没有共享资源**，host 骗人只能骗自己那半边。

捕鱼有三条它不满足的性质：

| 性质 | 后果 |
| --- | --- |
| 4 人 | `rooms` 只有 `hostId`/`guestId` 两个字段，房主一走整个房就 `closeRoom` 了 |
| 共享鱼池 | 同一条鱼被两人同时打中，必须有唯一裁决者；host 权威 = 房主永远先手 |
| 共享经济 | 金币是持久余额。客户端算出来的「我捕获了 5000 币」直接写库，等于把提款机接口暴露出去 |

所以这一款要在 `server/ws.mjs` 里加一层**游戏专属的权威房间**。好消息是：捕鱼的模拟量小到服务端完全跑得动（§3.4 算过）。

## 2. 核心循环

```
瞄准 → 开炮（扣 炮等级×1 金币）→ 网飞出去 → 命中鱼 → 服务端摇捕获判定
      ↓ 没中                                            ↓ 捕获
   钱没了，继续瞄                              金币 += 鱼价×炮等级，特效 + 音效
```

一次循环 0.3~1 秒。乐趣来自三层叠加：

1. **短周期**：瞄准命中的即时反馈（网炸开、鱼翻肚、金币飞向头像）。
2. **中周期**：炮等级选择。等级越高命中率越高但每发越贵，玩家一直在做「这条鱼值不值得升炮打」的决策——这是捕鱼类唯一的真决策，必须保留。
3. **长周期**：余额曲线。抓到 BOSS 鱼的一发回本感，是这类游戏的记忆点。

**多人在这里的增益**：抢鱼。一条 BOSS 鱼进场，4 个人的网同时糊上去，谁摇到谁拿走——这个瞬间是单机版给不了的。所以设计上必须让「别人打同一条鱼」高度可见：鱼身上要显示正在被几张网覆盖，捕获归属要全房广播（§5.3）。

## 3. 联机架构

### 3.1 权威划分

| 事项 | 谁说了算 |
| --- | --- |
| 鱼的生成、路径、离场 | 服务端 |
| 炮弹飞行与碰撞 | 服务端（客户端本地预演同一套，只为画面） |
| 捕获判定（摇概率） | 服务端 |
| 金币扣减与入账 | 服务端，且**只有服务端写库** |
| 瞄准角度、开炮时机 | 客户端（服务端只做频率与合法性校验） |
| 一切视觉、音效、飘字 | 客户端 |

一句话：**客户端只是一个带预测的显示器 + 输入设备。**

### 3.2 鱼为什么可以不逐帧同步

沿用霓虹突击那条地基（`COOP.md §2`）：**能推算的就不同步**。

每条鱼是一个纯函数 `pos(t) = path(kind, seed, t - t0)`——路径是预置的几条样条（横穿、S 形、环游、绕圈徘徊），参数在 `spawn` 消息里一次性带全。服务端和客户端跑**同一个 `sim/fish.ts`**，各自按时间求值即可。

代价是要有共享时钟：连上以后来回 5 次 `ping/pong` 取最短往返，估出 `serverTimeOffset`（和 `COOP.md §4.4` 同一套做法）。之后每 10 秒补一次，防时钟漂。

**不同步就意味着不需要 `sync` 校正消息**——这是纯函数相对于「服务端逐帧推位置」的实质好处：40 条鱼 × 20Hz 的位置广播（约 25KB/s/人）直接归零。

### 3.3 炮弹与捕获为什么必须服务端算

炮弹是匀速直线 + 侧壁反弹，也是可推算的，客户端本地立刻画出来（零延迟手感）。但**命中与捕获必须服务端复算**，因为它直接产钱。

服务端收到 `fire{angle, level, t}` 后：

1. 校验：`t` 是否在合理窗口内（±300ms）、距上一发是否 ≥ 冷却、余额是否够、`level` 是否是这个玩家当前的炮等级。
2. 扣钱：`balance -= level`。
3. 把这发炮弹放进自己的模拟。之后每 tick 与所有鱼做碰撞。
4. 命中 → 摇 `p = clamp(level / fish.value × K, 0, 0.9)`（`K` 是全局手感旋钮，见 §6.3）。
   - 中：广播 `caught{fishId, seat, gold}`，`balance += fish.value × level`。
   - 不中：广播 `pop{bulletId}`（网炸开但鱼没死）。

**关键：客户端本地不做捕获判定。** 网飞到鱼身上就炸开（这是玩家看到的即时反馈），鱼死不死等服务端那条 `caught`。往返 60~120ms 完全被网的爆炸动画（180ms）盖住，玩家感知不到。这是这套设计里唯一「必须忍」的延迟，而它恰好藏得住。

### 3.4 服务端负担

一房 4 人：鱼常驻 ≤ 40 条，炮弹 ≤ 4×4发/秒×2秒 = 32 发。20Hz tick 下碰撞检测 32×40×20 ≈ 25k 次/秒，纯数值运算。**一台 2 核云主机跑几十个房间毫无压力**——捕鱼的模拟量本来就极小，是这套「服务端全权威」方案成立的前提。

### 3.5 代码怎么共用

模拟必须两端跑同一份，否则鱼在客户端和服务端走两条路。

- 模拟层写在 `src/games/fish-hunter/sim/`，**纯 TS、零依赖、不碰 Phaser、不碰 DOM**。
- 浏览器侧直接 import。
- 服务端侧：`server/ws.mjs` 走 Node 24 的原生类型剥离直接 import `.ts`（本机 v24.13，`--experimental-strip-types` 已默认开启）。
- 因此 `sim/` 里**只许用「擦掉类型就是合法 JS」的写法**：不许 `enum`、不许 `namespace`、不许构造函数参数属性、不许 `import x = require()`。用 `const` 对象 + `as const` 代替 enum。

这条约束比引一套打包链轻得多，代价只是记住上面这句。

### 3.6 单机模式怎么办

单机不是另一套代码，是**把服务端塞进浏览器**：`sim/room.ts` 导出一个不依赖网络的 `FishRoom` 类，联机时跑在 Node 里，单机时跑在同一个 tab 的 `setInterval` 里，游戏层通过同一个 `Transport` 接口收发消息。

```
GameScene ── Transport ──┬── WsTransport   → server/ws.mjs → FishRoom（Node）
                         └── LocalTransport → FishRoom（浏览器内，同步调用）
```

好处：单机和联机的玩法永远一致，改一处两边都对；坏处：单机的金币也走 `FishRoom`，所以未登录用户的余额只能存 localStorage（`fish-hunter-wallet`），且**不与账号余额互通**——这一点要在 UI 上说清楚，别让人打了半天发现登录后钱没了。

## 4. 房间与座位

### 4.1 对 `server/ws.mjs` 的改动

现有的 `rooms` 是 `{ hostId, guestId }`，要改成：

```js
{ id, game, seats: [userId|null, userId|null, userId|null, userId|null], hostId, started, engine }
```

- `seats` 定长 4，索引即座位号。**座位号决定炮台位置**，不能靠加入顺序临时算——中途有人走了，剩下的人不能被挪位置。
- `engine`：`game === 'fish-hunter'` 时挂一个 `FishRoom` 实例；其他游戏为 `null`，行为和现在完全一致（`case 'game'` 继续走纯转发）。
- `closeRoom` 的语义要改：**不再是「一个人走全房散」**。走的人清空自己的座位，房间只在座位全空时销毁。房主走了就把 `hostId` 转给还在的第一个人。

改动是加法，`peerOf` 这类双人假设的辅助函数只在非 `fish-hunter` 分支里用，霓虹突击不受影响。

### 4.2 大厅

现有大厅是「点某个在线用户 → 定向邀请」的 1v1 模型，捕鱼要的是**开放房列表**：

- `t: 'rooms'` —— 列出 `game === 'fish-hunter'` 且有空座的房间（房号、人数、已开局与否）。
- `t: 'create'` / `t: 'join'{roomId}` —— 建房 / 占座，占不到（满了/同时点）返回 `error`。
- 沿用现有的定向 `invite`：好友直接拉人进房，不用报房号。
- **捕鱼没有「开局」这个时刻**——房建好鱼就在游，人随进随打。所以 `started` 对这一款没有意义，`start` 消息不用。这也是它比霓虹突击好做的地方：不用等所有人准备。

### 4.3 座位布局（横屏 1280×800）

横屏是这类游戏的原生形态，理由不是「传统如此」，而是三条实打实的：

1. **鱼横向游动**，横屏意味着每条鱼在场时间更长、可打窗口更宽；竖屏下鱼几秒就穿场了。
2. **4 个炮台要沿两条长边排开**才不互相挡视野。竖屏的短边塞两门炮，炮台会占掉画面很大一块。
3. **瞄准是全屏点击**，横屏的可视鱼池面积大，"该打哪条"的决策空间才成立。

```
┌────────────────────────────────────────────────────┐
│ [座2]                                       [座3]  │ ← 上方两人，界面整体旋转 180°
│  ↓炮                                         ↓炮   │
│                                                    │
│   ~~~~~~~~~~~ 鱼 群 横 向 游 动 ~~~~~~~~~~~~~~     │
│                                                    │
│  ↑炮                                         ↑炮   │
│ [座0] 余额/炮等级/换炮            余额/... [座1]   │ ← 下方两人
└────────────────────────────────────────────────────┘
```

- 座位号由服务端分配且固定（§4.1），但**渲染时做一次本地映射把自己换到下方**（座 0 或座 1），上方两人的炮台、飘字、余额条整体旋转 180° 绘制。谁都不会对着倒过来的界面玩。
- 1280×800（16:10）而不是 16:9：`PhaserCanvas` 的横屏分支已经是 `aspect-[8/5]`，直接对上，非全屏时不用改组件。

#### 屏幕方向怎么处理

盒子里现有的游戏都是竖屏，`src/app/manifest.ts` 里写死了 `orientation: 'portrait'`，装成 PWA 后系统会锁竖屏。这一款要动到三处：

- **manifest 改成 `orientation: 'any'`**，把方向决定权交回各游戏页。竖屏那几款本来就不依赖这个锁（它们的画布是 `aspect-[9/16]`，横过来只是两侧留白），改成 `any` 不会破坏它们。
- **游戏页 `fullscreen` 挂载**（照 `neon-strike-2d/page.tsx` 的写法，但不传 `orientation="portrait"`），进入时尝试 `screen.orientation.lock('landscape')`。这个 API 只在全屏态下生效、且 iOS Safari 不支持——**所以它是加分项不是依赖项**。
- **兜底是引导页**：检测到 `innerHeight > innerWidth` 就盖一层「请横过手机」提示，转回来自动消失。iOS 只能走这条路。

大厅页（`/fish-hunter/lobby`）保持竖屏可用——选房是普通网页交互，没必要也强制横屏。

## 5. 局内协议

服务端 → 客户端：

| 消息 | 说明 |
| --- | --- |
| `hello{seat, seats[], balance, serverTime}` | 进房快照。`seats` 带用户名和炮等级 |
| `spawn{id, kind, pathId, seed, t0, speed, flip}` | 鱼进场。**随机参数一次带全**，之后不再同步 |
| `despawn{ids[]}` | 鱼游出界，批量 |
| `fired{seat, bulletId, angle, level, t}` | 别人开炮了（自己那发不回传，本地已画） |
| `pop{bulletId}` | 网炸开但没捕到 |
| `caught{fishId, bulletId, seat, gold}` | 捕获。全房广播，谁抓的写在飘字上 |
| `wallet{balance}` | 只发给本人。**余额只认这条**，客户端不自增 |
| `seat{seat, user|null, level}` | 有人进/出/换炮 |
| `special{kind, ...}` | 全屏技（冰冻、闪电链）触发 |
| `deny{reason}` | 开炮被拒：余额不足 / 太快 / 参数非法 |

客户端 → 服务端：

| 消息 | 说明 |
| --- | --- |
| `fire{angle, t}` | 开炮。`level` 不带——服务端知道你的炮等级，带了也不信 |
| `level{delta}` | 换炮 |
| `aim{angle}` | 炮口朝向，8Hz，纯表现。**丢了不影响任何判定** |
| `ping{id}` / `pong` | 时钟对齐 |

带宽估算（4 人房，每人）：鱼 spawn ≈ 2 条/秒 × 80B，fired ≈ 12 条/秒 × 40B，aim ≈ 24 条/秒 × 20B，caught ≈ 3 条/秒。**合计不到 2KB/s**。这就是「能推算的就不同步」的收益。

## 6. 数值

### 6.1 鱼

| 种类 | 价值 | 血/难度体现 | 出现权重 | 说明 |
| --- | --- | --- | --- | --- |
| 小丑鱼 | 2 | — | 40% | 成群出现，垫底收益 |
| 蓝鳍鱼 | 5 | — | 25% | |
| 河豚 | 10 | — | 15% | 被网碰到会鼓起来（判定圈变大 1.4×，短暂） |
| 海龟 | 20 | — | 10% | 慢，好打 |
| 魔鬼鱼 | 40 | — | 6% | 走 S 形，难瞄 |
| 鲨鱼 | 80 | — | 3% | 快 |
| 金龙 | 200 | — | 0.8% | 稀有，全房播报进场 |
| BOSS 章鱼 | 500 | 分 8 段判定圈 | 每 3 分钟必来一次 | 停留 25 秒，四个人一起打 |

**没有血条**——捕鱼类的「难打」不是靠扣血，是靠低捕获概率。加血条会让高价值鱼变成「谁最后一发运气好」的抢尾，体验更差。

### 6.2 炮

炮等级 1~7。每发成本 = 等级，捕获收益 = 鱼价 × 等级。

### 6.3 捕获概率与 RTP

```
p = clamp(level / fish.value × K, 0.01, 0.9)
```

`K = 1.0` 时数学期望正好回本（`p × value × level == level`）。**实际取 `K = 0.92`**，即 92% RTP：长期缓慢下滑，逼玩家在鱼群密度高时才开炮，而不是无脑长按。8% 的抽水就是这款游戏的「难度」。

这个值是**唯一的经济总旋钮**，调它之前先想清楚要往哪边动：调高 → 玩家一直变富，金币失去意义；调低 → 频繁见底、频繁吃补助，补助反而成了主要收入。

### 6.4 破产

余额 < 最低炮等级成本时，服务端直接补到 200，冷却 10 分钟一次。

理由直接来自 §0 的「不做充值」：既然没有付费复活这条路，**卡住玩家就是纯粹的流失**，没有任何收益。补助要给得干脆——不弹「观看广告」、不弹「明日再来」，静默补到位加一句飘字即可。冷却存在的唯一目的是防止有人用「打空→立刻补→再打空」刷金币，不是为了制造焦虑。

### 6.5 全屏技

- **冰冻**：全场鱼减速 70%，持续 6 秒。由「捕获金龙」小概率触发，全房共享效果——**别人打出来自己也吃到**，这是让 4 人同池感觉像「一起玩」而不是「各打各的」的关键设计。
- **闪电链**：网命中时 5% 概率向最近 3 条鱼各补一次判定。

## 7. 视听（细则交给 game_artist 写 ART.md）

- 背景：深海渐变 + 缓动光柱 + 浮游粒子，全部运行时生成，不占素材。
- 鱼：**这一款必须用真图**——8 种鱼靠 `Graphics` 画不出辨识度，而辨识度直接决定玩家能不能瞬间判断「这条值不值得打」。走 ComfyUI 出侧视图 PNG（透明底），落 `public/fish-hunter/fish/*.png`。游动摆尾用 Phaser 的 `rope` 沿身体做正弦位移，不做逐帧序列图（8 种鱼 × 序列帧 = 素材体积失控）。
- 炮台、网、金币：`Graphics.generateTexture()` 生成，够用。
- 音效：rFXGen，`tools/audio/fish-hunter/build_sfx.mjs`，参照霓虹突击那套流程。清单：开炮、网炸开、捕获小鱼、捕获大鱼、金龙进场、冰冻、余额不足。
- **可读性红线**：4 个人的网同时在场时画面很容易糊。每个座位一个固定色（青/橙/紫/绿），网、炮台、飘字全部用该色；捕获飘字只在自己捕获时用大号，别人的用小号半透明。
- **横屏带来的两条额外约束**：一是鱼的侧视图素材要按横向游动出图（朝左/朝右各一份，或出一份靠 `flipX`）；二是上下两排炮台各占约 110px 高，中间留给鱼池的净高只有约 580px，**大型鱼（金龙、BOSS 章鱼）的贴图高度不能超过 260px**，否则同屏两条大鱼就把鱼池糊死了。

## 8. 落地顺序

每一步都是可玩的，不做「全做完才能跑」的大爆炸。

1. **单机跑通**：`sim/`（鱼路径、炮弹、碰撞、捕获摇点、钱包）+ `LocalTransport` + Phaser 场景。此时已经是一款完整的单机捕鱼。
2. **服务端房间**：`server/ws.mjs` 改多座位 + 挂 `FishRoom` + 协议 §5。`WsTransport` 接上。两人同池能互相看到网和捕获。
3. **大厅**：房列表 / 建房 / 加入 / 邀请，`CoopProvider` 补 `fish-hunter` 分支。
4. **金币入库**：`scripts/db/schema.sql` 加 `wallets` 表（`user_id` 主键、`balance`、`updated_at`、`last_grant_at`），服务端**批量落盘**（每 10 秒或余额变动 > 500 时写一次，进程退出时 flush）——每发炮弹写一次库是没必要的写放大。
5. **打磨**：全屏技、BOSS、破产补助、音效、断线重连（重连即重新 `hello` 拿快照，鱼池本来就在服务端，没有恢复难题）。

## 9. 验收

- 4 个人同池，同一条 BOSS 鱼四张网同时命中，只有一个人拿到金币，且四端看到的归属一致。
- 客户端改 JS 伪造 `caught` / 直接改本地余额显示，刷新后余额回到服务端的真值，且**服务端账本从未被写脏**。
- 网络延迟注入 200ms：开炮手感无变化（网立刻飞出去），只有金币飘字晚一拍。
- 房主退出，剩下三人继续打，鱼不中断，房不解散。
- 断网 5 秒后重连：余额正确、鱼池正确、自己的座位还在。
- 不登录直接进：单机模式可玩，且明确告知余额不与账号互通。
- 手机竖着打开游戏页：显示「请横过手机」引导，转成横屏后自动进入且画布铺满；改 manifest 后其余竖屏游戏表现不变。
- 全站搜不到任何充值、商店、价格、IAP 相关的代码路径与文案。
- 挂机长按开炮 20 分钟，余额单调下滑到触发补助，补助后不能立刻再触发。
