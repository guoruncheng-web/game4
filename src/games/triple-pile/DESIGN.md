# 叠叠消(Triple Pile)产品设计

> 本文档定「游戏应该是什么样」。工程组织见 `ARCHITECTURE.md`,视听规格见 `ART.md`。
>
> **与 `tumble-stack` 的关系:两款是完全独立的游戏,不共享一行代码、也不共享任何素材。**
> 早期版本曾计划复用 `tumble-stack/ART.md` 的火锅配方(程序化顶点色),
> 后来改成用户提供的写实素材 + Blender 低模,那条关联已经不存在了。

## 1. 产品定位

- **类型**:3D 三消 / Triple Match(「三个一组」那一支,不是「三连线」那一支)。
- **平台**:手机竖屏浏览器为主,桌面浏览器用居中的竖屏画布(**540×960 逻辑分辨率**)。
- **渲染**:**Three.js**(透视相机、俯视机位、Lambert 材质、无阴影贴图、无后处理)。
- **物理**:**Rapier(`@dimforge/rapier3d-compat`,WASM)**。不使用 Phaser。
- **目标时长**:单关 1–3 分钟,进游戏 8 秒内已经消掉第一组。
- **核心体验**:从一锅乱堆的食材里**认出、点走、凑齐三个**;拿走一个,压在上面的塌下来,露出新的一层 ——
  **秩序感 + 一点点考古学**(MDA 美学中的 Challenge + Discovery,其次 Sensation)。
  玩家追求的是「我把这一锅理清楚了」,以及「拿走这块之后底下露出来的正好是我缺的那个」。
- **在游戏盒子里的定位**:盒子里第一款**慢节奏、无反射弧、纯认知负荷**的游戏。
  现有几款(跳跃、挥砍、射击、台球)全部考手眼协调,本作考的是**辨识与记忆**。
- **设计边界**:不做账号、养成、关卡编辑、联网排行、**任何形式的付费与广告**。

### 1.1 与 tumble-stack 的玩法分界(为什么是两款而不是一款的两个模式)

| | 本作 叠叠消 | tumble-stack 叠叠崩 |
| --- | --- | --- |
| 输入 | **点选**场上物件 | 拖动瞄准、松手投放 |
| 消除条件 | 收进槽位**凑齐 3 个同类** | 场上 3 个同类**互相接触** |
| 物理的作用 | 铺出初始堆 + 拿走后的**塌落** | **玩法核心**,砸/滚/连锁塌方 |
| 相机 | 俯视锅口 | 侧视竖井 |
| 失败 | 槽位 7 格塞满 / 超时 | 堆超过警戒线 |
| 结构 | **关卡制**,清空即通关 | 无尽刷分 |
| 核心快感 | 归类清空的秩序感 | 不可控的塌方连锁 |

两作唯一真正相通的只有「3 个同类」这个词,而它在两边指的是完全不同的判定。
**本作不需要查询接触对**,所以 `tumble-stack/ARCHITECTURE.md` §0 那条阻塞验证
(休眠刚体的 contact pair 是否保留)在本作中**不存在**,不要照抄那条前置任务。

- **一句话概括**:从一锅堆在一起的火锅食材里点走同类,三个一组消掉,把锅清空。
- **卡片 tagline**(写进 `registry.ts`):`俯视火锅捞菜 · 三个一组消除 · 拿走就塌`

## 3. 核心循环

### 3.1 微循环(约 2–5 秒,一次「看-认-点-归位」)

1. 玩家俯视一锅堆叠的食材,视线在表层扫描。
2. 点中一个 → 它**从堆里被拔出来**,沿一条弧线飞到屏幕底部的槽位条。
3. 同时,原本压在它上面/靠着它的食材**失去支撑塌下来**,露出下面一层。
4. 槽位条里同类自动靠拢排在一起。
5. 凑齐 3 个 → 这 3 个一起**炸掉**,槽位右侧的整体左移,腾出格子。

**这个微循环的命根子是第 2–3 步之间的因果可见性。**
玩家必须看清「我拿走的是这一个」和「因此塌下来的是那几个」。
拔出动画太快 = 看不清拿了什么;塌落太剧烈 = 整锅重排,玩家刚建立的空间记忆全部作废。
**塌落必须是局部的、小幅的**(§7.2),这是本作最重要的手感约束。

### 3.2 中循环(一关 1–3 分钟)

开局 → 表层好认的先拿 → 槽位开始占位 → 中期出现「我缺的那个被压在底下」的僵局 →
用道具或换个方向拆表层 → 后期锅里只剩零星几个,快速清空 → 结算。

**难度不来自手速,来自「槽位占位」与「视野遮挡」的夹角**:
你想拿的拿不到,能拿的又不想要 —— 每占掉一格,容错就少一格。

### 3.3 宏循环(关卡推进)

关卡制,共 **12 关**(MVP)。每关的物件总数、类型数、限时按 §9 递增。
通关后解锁下一关;已通关的关卡可以重玩刷时间。**没有体力、没有解锁付费、没有星级三档评价**——
只记录「最快通关用时」。

## 4. 场地与相机

### 4.1 场地

- 一口**圆锅**,内半径 `R = 4.2`,内壁高 `H = 3.0`,锅底 `y = 0`。
- 锅壁用 **24 段的静态 collider 环**近似圆(不要 trimesh,不要真圆柱 collider ——
  Rapier 的圆柱 collider 内侧不能当容器用)。24 段在 R=4.2 下的最大弦高误差约 0.036,
  小于最小物件半径的 1/10,玩家看不出来。
- 锅底是一个静态 `cuboid`,不是圆盘。物件不会掉到锅外,圆锅壁已经兜住。
- 视觉上锅口外还有桌面、配菜碟、蘸料碗(见 `ART.md`),**全部是纯装饰,没有碰撞体**。

### 4.2 相机

- `PerspectiveCamera`,**俯角 62°**(不是正俯视 90°)。
  - 正俯视会让所有物件退化成剪影,厚度信息全丢 —— 而本作的辨识完全依赖造型。
  - 俯角小于 55° 会让后排被前排挡住太多,锅底看不见。
  - **62° 是「能看出厚度」和「能看到锅底」的交点**,实现时允许在 58°–66° 内微调,定下来后写死。
- `fov = 55`,`lookAt(0, 1.0, 0)`。**相机距离不写死,按容器宽高比算出来**(`stage.ts` 的 `fitDistance`):
  竖屏 9:16 下水平视野远窄于垂直视野,写死距离会把锅切掉两边。俯角保持不变,只调距离。
- **相机全程不动。** 不做旋转、不做缩放、不做跟随。
  理由:本作要求玩家建立「哪个东西在哪」的空间记忆,任何相机变换都会毁掉这份记忆。
  这一条是硬性的,即使后期有人提「能不能转一转看背面」也不加 —— 那是另一款游戏。

### 4.3 「看不见就拿不到」是规则,不是限制

玩家只能点中**当前可见**的物件(§6.1 用 raycast 天然实现)。
被完全压住的物件必须先把上面的拿走。这就是本作的全部空间挑战,不需要额外加锁定机制。

## 5. 物件类型

### 5.1 12 类,全部来自写实素材

物件是 12 种火锅食材,模型由 `tools/blender/triple-pile/build_models.py` 从 12 张
正视图渲染(`assets/source/*-chroma.png`)生成,产物在 `public/triple-pile/models/*.glb`。
造型细节与生成管线见 `ART.md`。

| # | key | 名称 | 形体 | 独立于颜色的识别特征 |
| ---: | --- | --- | --- | --- |
| 0 | `beef-roll` | 肥牛卷 | 竖立圆卷 | 红白脂纹(灰度下是斑马纹) |
| 1 | `lettuce` | 生菜 | 球 | 同心叶片 |
| 2 | `tofu` | 豆腐 | 立方体 | 唯一的直角形体 |
| 3 | `shiitake` | 香菇 | 半球伞盖 | **白色十字花刀**(全场最高的局部对比) |
| 4 | `corn` | 玉米 | 短圆柱(截面朝外) | 放射状玉米粒 |
| 5 | `lotus-root` | 藕片 | 薄圆盘 | **一圈通透的孔**(唯一有洞的物件) |
| 6 | `sausage` | 香肠 | 横胶囊 | 纯色、两端收口 |
| 7 | `crab-stick` | 蟹棒 | 斜置圆柱 | 红白沿轴扭转 |
| 8 | `napa-cabbage` | 白菜 | 长椭球 | 绿叶白帮的纵向分区 |
| 9 | `fish-ball` | 鱼丸 | 球 | 橙色颗粒点缀 |
| 10 | `tofu-skin-roll` | 腐竹卷 | 横卷 | 端面的卷心洞 |
| 11 | `dumpling` | 饺子 | 扁半月 | 一侧的褶皱边 |

**id 顺序不要重排** —— 关卡生成和 `TYPE_ORDER` 都按 id 索引。

### 5.2 为什么 12 类是可行的(初版设计定的是 6 类)

初版把 MVP 锁在 6 类,主要理由是「火锅题材的色域只够 6 类」——
那是**平面顶点色路线**下的结论:每个物件只有一个色块可用,色相和明度都不够分。

换成写实贴图之后这条限制消失了:每个食材自带独有的纹理与结构,
识别不再只依赖色相和明度。所以 12 类全上。

新的可读性风险变成另外两条(缓解办法见 `ART.md` §4):
- **豆腐 / 鱼丸 / 饺子**都是浅米白,只能靠轮廓分;
- **生菜 vs 白菜**、**香肠 vs 蟹棒 vs 肥牛卷**两组同色系。

`TYPE_ORDER` 把最难认的三样排在最后,它们只在第 10 关之后才同时出现。

### 5.3 碰撞体:模型顶点的凸包

**不再单独维护一套碰撞体。** 建模脚本保证 12 个模型全是凸体,
运行时直接对模型顶点求凸包(`RAPIER.ColliderDesc.convexHull`)就是精确的碰撞体。

这样「视觉超出碰撞体」这类问题在结构上不可能发生 —— 而在一个消除规则完全建立在
「看得见就点得到」上的游戏里,那是可读性的头号红线。

**全部 collider 必须是凸的**,这条依然是硬约束:凹形需要 compound collider,
接触点数量翻倍、稳定性下降。改建模脚本时不要引入凹形体。

### 5.4 质量:全类型统一,不按密度

所有物件质量统一钉死在 **0.73**(`PIECE_MASS`),用 `setMass` 而不是 `setDensity`。

这不是物理真实性,是**稳定性旋钮**:12 个模型的体积差了好几倍(蟹棒 vs 藕片),
按密度给会让任意两类的质量比远超 2:1,而高质量比会让求解器在堆叠时明显抖动 ——
轻的物件被压在重的下面时,接触冲量会来回震荡。

## 6. 拾取与槽位(核心规则)

### 6.1 拾取

- 点击/触摸 → `Raycaster` 从相机打向指针,取**最近命中**的物件。
- 命中即拿走,**没有二次确认、没有长按、没有拖拽**。三消的手感就建立在「点哪个走哪个」的即时性上。
- 被拿走的物件立刻从物理世界移除刚体(不是设成 kinematic 后留着),
  然后作为纯 mesh 播 0.32s 的飞行动画进槽位。
  - **必须真的移除刚体**,否则它在飞行途中仍然参与碰撞,会把堆撞散。
- 飞行途中**允许继续点下一个**。不做输入锁 —— 锁输入是本类游戏最常见的手感杀手。
- 飞行动画:一条二次贝塞尔,控制点在物件与槽位中点的上方 `+1.8`,同时物件旋转到**正面朝向相机的标准姿态**。
  这个「归位旋转」很重要:槽位里的东西必须以统一姿态陈列,玩家才能一眼数清各有几个。

### 6.2 槽位条

- **7 格**,固定在画布底部。
- 新收的物件插入到**同类的最右侧**;没有同类就排到最右端。
  - 这条是三消的通用惯例,作用是让玩家不用扫描整条槽位就能看出「这类我有几个了」。
- 凑齐 3 个同类 → 延迟 **120ms** 后三个一起消除,右侧整体左移补位。
  - 这 120ms 是给玩家看清「是它凑齐了」的时间,不能省。
- 槽位里的物件是**真 3D mesh**(复用同一份 geometry),不是 2D 图标。
  它们摆在相机前方一排固定的世界坐标上,不受物理影响。
  - 好处:零额外资源、造型与锅里完全一致(辨识一致性)、能看出厚度。

### 6.3 消除

- 3 个同类同时炸掉,播粒子 + 音效 + 分数飘字。
- **没有连锁**。本作的消除是离散事件,不做 combo 倍率链。
  理由:连锁奖励会逼玩家憋牌,而憋牌在只有 7 格的槽位里是纯粹的自杀策略,
  设计一个「奖励你去死」的机制没有意义。
- 有 **连续消除计时奖励**:两次消除间隔 < 3s 记一次 `quick`,只影响分数(§11),不影响生存。

## 7. 物理的角色

### 7.1 物理只在两个时刻真正工作

1. **开局铺堆**:物件从锅口上方分批落下,自然堆成一锅。
2. **拿走之后的塌落**:失去支撑的物件塌下来。

其余时间整锅是静止的。**允许并鼓励刚体休眠** —— 本作不查询接触对,休眠没有任何副作用。
这是与 `tumble-stack` 最重要的工程差异,它把那边的头号技术风险直接消掉了。

### 7.2 塌落必须是局部的、小幅的(手感红线)

拿走一个之后,如果整锅重排,玩家的空间记忆全部作废,游戏立刻变成纯随机点击。
控制手段:

| 参数 | 值 | 作用 |
| --- | --- | --- |
| 重力 | `-14` | 比 tumble-stack 的 20 小。落得慢一点,塌落过程看得清 |
| `restitution` | `0.02` | 几乎不弹。弹跳是「整锅重排」的头号来源 |
| `friction` | `0.75` | 高摩擦,东西倾向于卡住而不是滑走 |
| `linearDamping` | `0.6` | 让塌落快速收敛 |
| `angularDamping` | `2.2` | 强角阻尼,东西不会一直滚 |
| 休眠阈值 | Rapier 默认 | 塌完就睡,省 CPU |

**验收标准:拿走表层一个物件后,位置变化超过 0.3 的物件数量不应超过 4 个。**
超了就把 `friction` 和 `angularDamping` 往上调。这条要在实现后实测,不是拍脑袋。

### 7.3 开局铺堆是确定性的吗

**不是,也不需要是。** 每关的物件构成(各类型几个)是固定的,但堆出来的形状每次不同。
这正是重玩价值的来源。**但必须保证「一定能通关」** —— 见 §8.2。

## 8. 槽位数学与失败条件

### 8.1 为什么 7 格是可以塞满的(鸽笼论证)

槽位塞满而无法消除,要求每一类在槽位里都**只有 1 个或 2 个**(有 3 个就消掉了)。
设类型数 `K`,槽位数 `N`:

- 最坏情况下槽位能容纳的「不消除物件」上限是 `2K`。
- 所以 **`2K ≥ N` 时才可能塞满失败**,即 `K ≥ ⌈N/2⌉`。
- `N = 7` → `K ≥ 4`。

**所以第 2 关(4 类)才是第一个可能死于槽位的关卡**,而第 1 关的 3 类**在数学上不可能塞满** ——
这正是 §9 让第 1 关用 3 类的原因:新手只可能超时,不会死于自己还不理解的规则。
典型死局:3 类各 2 个 + 另外 1 类 1 个 = 7 格。

反过来这也说明**槽位数不能随手改**:加到 12 需要 `K ≥ 6`,前四关就全都不可能输了;
减到 5 只需 `K ≥ 3`,第一关就会开始死人。**7 格是被这个不等式选出来的,不是抄的。**

这条结论已用 2400 局随机盲打验证过:K=3 时永远塞不满,K≥4 时会出现死局。

### 8.2 每关必须可解(硬性约束)

- **每关每种类型的数量必须是 3 的倍数**,总数也因此是 3 的倍数。
  否则关卡末尾会剩下 1–2 个永远消不掉的物件,槽位被永久占用 —— 这是本类游戏最经典的崩关 bug。
- 生成关卡数据时**先按 3 的倍数配好各类型数量,再打乱投放顺序**,不允许运行时随机决定类型。
- 这条要写进单元可验证的断言:`counts.every(c => c % 3 === 0)`。

### 8.3 失败条件

1. **槽位 7 格占满且无同类可凑** → 立即失败。
2. **限时归零** → 失败。

失败后可以**原地重开本关**(重新铺堆),不消耗任何资源,不看广告。

### 8.4 通关条件

锅里物件全部清空,且槽位为空。因为 §8.2 保证了 3 的倍数,这两件事必然同时发生。

| 3 | 5 | 30 | 2:50 | |

## 10. 道具

三个道具,**每关各 1 次,用完即止,不能购买、不能看广告补充、局间不累积**。
UI 上不出现 `+` 号,用完的按钮变灰。

| 道具 | 效果 | 为什么需要它 |
| --- | --- | --- |
| **移出** | 把槽位里**最左边的 3 个**退回锅里(从锅口上方重新落下) | 唯一能解「槽位快满了」的手段。退回而不是删除,保证 §8.2 的 3 的倍数不被破坏 |
| **凑齐** | 从锅里自动找出与槽位中**数量最多的那一类**同类的物件,补满到 3 个并消除 | 解「我缺的那个被压在最底下」这个僵局。它消解的是遮挡,不是判断 |
| **打乱** | 把锅里所有物件**重新抛起落下**,重新堆一次 | 解「表层全是我不需要的」。代价是玩家的空间记忆全部作废 —— 这是它的天然成本,不需要额外惩罚 |

- **「移出」退回锅里而不是丢弃**,这条是硬的。丢弃会让某类型的剩余数量不再是 3 的倍数,直接崩关。
- **「凑齐」必须真的从锅里取物件**,不能凭空生成 —— 同理。
- **「打乱」不改变任何数量**,天然安全。
- 三个道具都不影响计时(不暂停也不加时)。

## 11. 计时与计分

- 关卡限时倒计时,归零即失败。**不做「时间到了扣分继续玩」这种软失败。**
- 分数只在结算页展示,不做实时飘涨的大数字(那会抢走视线,而本作的视线全部属于锅)。

| 项 | 分值 |
| --- | ---: |
| 每次三消 | +100 |
| 间隔 < 3s 的连续消除(`quick`) | 每次额外 +50 |
| 通关剩余时间 | 每剩 1 秒 +10 |
| 未使用的道具 | 每个 +200 |

「未使用道具加分」是刻意的:它让道具变成**有成本的选择**而不是无脑点击,
同时不惩罚真正需要它的玩家(用了也能通关,只是分低)。

## 12. 持久化

- `triple-pile-progress`:`{ unlocked: number }`,已解锁到第几关。
- `triple-pile-stats`:`{ best: Record<levelId, { score: number; timeMs: number }> }`。
- 读写走各游戏自己的 `storage.ts`,包 `try/catch`,判 `typeof localStorage === 'undefined'`;
  **解析失败或值不认识 → 回退到「只解锁第 1 关」,不影响开局。**
- 复用全站键 `game-box-muted` / `game-box-volume` 控制音量。

## 13. 输入

- **触摸/鼠标点击**是唯一的核心输入。没有拖拽、没有手势。
- `P` / `ESC` 暂停。
- 道具用点击按钮触发,**不给键盘快捷键** —— 道具是需要犹豫一下的决定,不该做得太顺手。
- 点击判定用 `pointerup` 而不是 `pointerdown`,并要求 `pointerdown` 与 `pointerup` 之间
  指针移动小于 12px。这样误触时可以「按下去发现点错了,滑开再松手」取消。

## 14. 引导

不做独立教学关,不做遮罩式分步引导。**第 1 关本身就是教学**:

- 3 类、18 个、3 分钟,不可能死于槽位。
- 首次进入时,槽位条上方显示一行文字提示:`点食材放进下方格子 · 凑齐 3 个就消`。
  玩家完成第一次三消后淡出,此后不再出现(记进 `triple-pile-progress`)。
- 道具按钮在第 3 关(首次可能塞满的那关)才出现并高亮一次。
  前两关不显示 —— 新手不需要在还没理解规则时面对三个不知道干什么的按钮。

## 15. 性能预算

- **draw call 与物件数量脱钩**:12 个类型 = 12 个 `InstancedMesh`,
  无论场上是 18 个还是 120 个物件。贴图数量等于**类型数**,不等于物件数。

| 项 | draw call |
| --- | ---: |
| 12 类物件 `InstancedMesh` | 12 |
| 锅体(merge) | 1 |
| 桌面 + 装饰碟(merge) | 1 |
| 槽位底板(instanced) | 1 |
| 粒子主系统 / 火花系统 | 2 |
| 拾取描边 | 1 |
| 消除打白(最多 3 个) | 3 |
| **合计** | **21** |

- 三角面:12 个模型合计 804 三角,满场 120 个约 **8000 三角/帧**,余量极大。
- 素材体积:12 个 glb 合计约 **4.3MB**(贴图内嵌,长边 512)。
  由 Service Worker 按「玩过才缓存」策略处理,不做安装时预下载。
- **Rapier 才是真瓶颈**:120 个凸体的堆叠求解是最重的一块。
  控制手段是让堆尽快休眠(§7.2 的高阻尼)。实现后必须实测第 12 关满堆时的 step 耗时,
  目标 **< 4ms**。

## 16. 明确不做(范围控制)

- 不做主题选择器(火锅一套即可,§5.4)。
- 不做第 7 类及以上(触发条件:12 关全部实现并实测通关率合理之后,再评估)。
- 不做相机旋转/缩放(§4.2,这是设计决定不是偷懒)。
- 不做连锁倍率(§6.3)。
- 不做付费、广告、体力、每日任务、排行榜。
- 不做关卡内的特殊物件(冰冻、锁链、炸弹)。这些是加法,先把 12 关的基础曲线做对。

## 17. 验收清单

实现完成后逐条验证,任何一条不过就不算做完:

1. 每关每类型数量都是 3 的倍数(`counts.every(c => c % 3 === 0)`)。
2. 通关时锅里为空**且**槽位为空,两者同时发生。
3. 槽位塞满 7 格且无同类 → 立即判负,不卡死在可操作状态。
4. 「移出」把 3 个退回锅里之后,该类型剩余总数仍是 3 的倍数。
5. 「凑齐」在锅里同类不足时**不能凭空生成**,应当置灰不可用。
6. 拿走一个物件后,位移 > 0.3 的其他物件不超过 4 个(§7.2)。
7. 飞行动画途中连续快速点击 5 个物件,不丢输入、不重复拾取同一个。
8. 被拿走的物件的刚体确实从物理世界移除(不再参与碰撞)。
9. 12 类物件在**任意朝向**下都能辨认,包括完全背对相机时(`ART.md` §0.3)。
10. 灰度截图下,`ART.md` §4 那两组同色系仍可区分。
11. 第 1 关不可能死于槽位塞满(3 类,§8.1)。
12. 重开一关后,道具次数、计时、分数全部重置,没有跨局泄漏。
13. 第 12 关满堆(120 物件)时 Rapier step < 4ms,整体 60fps。
14. 暂停时物理与计时都停,恢复后不出现「补帧」导致的整锅炸开。
