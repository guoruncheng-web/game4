# 叠叠崩(Tumble Stack)产品设计

## 1. 产品定位

- **类型**:单人物理堆叠消除 / 无尽刷分。
- **平台**:手机竖屏浏览器为主,桌面浏览器使用居中的竖屏画布(**540×960 逻辑分辨率**)。
- **渲染**:**Three.js**(透视相机、Lambert 材质、两盏灯、无阴影贴图、无后处理)。
- **物理**:**Rapier(`@dimforge/rapier3d-compat`,WASM)**。不使用 Phaser。
- **目标时长**:单局 2–5 分钟,进游戏 10 秒内已经消掉第一组。
- **核心体验**:把一块东西丢下去,它砸、滚、卡住、然后整堆塌下来连着炸三次 —— **可控的意外**(MDA 美学中的 Sensation + Challenge,其次 Discovery)。玩家追求的不是精确落点,而是「我预判到了这一塌」。
- **在游戏盒子里的定位**:现有三款(star-runner 跳跃、fruit-slasher 挥砍、neon-strike 射击)全部是 2D 反射弧动作类。本作是盒子里**第一款真 3D、第一款刚体物理、第一款慢节奏思考型**。它和另外三款在节奏、维度、输入密度上全部错开。
- **设计边界**:不做账号、道具、养成、关卡编辑、联网排行、付费、道具复活。

## 2. 命名与标识

- **中文名**:叠叠崩
- **英文名**:Tumble Stack
- **slug**:`tumble-stack`
- **一句话概括**:往一个竖井里丢不同形状的方块,让 3 个同类互相碰到就炸,炸完上面塌下来接着炸。
- **卡片 tagline**(写进 registry):`真 3D 刚体堆叠 · 三连接触即爆 · 连锁塌方`
- **controls**:`按住拖动瞄准 · 松手投放 · ← → 移动 · 空格投放`
- **accent**:`text-violet-400`
- **持久化键**:`tumble-stack-best`(数字)、`tumble-stack-stats`(JSON),见 §12。

> slug 说明:`tumble` 指的正是本作的卖点 —— 塌方连锁,而不是「堆起来」。命名取玩法高潮,不取玩法动作。

## 3. 核心循环

### 3.1 微循环(约 3–8 秒,一次「看-瞄-放-看结果」)

1. 竖井顶部悬着**当前这块**(半透明 ghost + 实体),HUD 右上角显示**下一块**。
2. 玩家按住屏幕任意处 → 瞄准器横向跟随手指;一条落点光束从块底垂直射到下方第一个受力面,并在那里画一个椭圆落点标记。
3. 松手 → 块以 -1.5 的初速自由落体。
4. 它砸下去:撞击粒子、闷响、周围的块被推开一点点、堆晃两下。
5. 如果这一下让 3 个同类互相接触 → 爆。没爆的话,玩家立刻看到**「差一个」的提示**:任意两个已经稳定接触的同类块会共享一次低频呼吸辉光(见 §10.2),这就是「这两个算接上了」的可读性来源。

**这个微循环的命根子是第 3–4 步的落体手感。** 重力 20、极低弹性、强角阻尼 —— 块落下去要「砸实」,不能弹、不能飘、不能像纸片一样滑走。任何一处不对,后面的连锁系统都救不回来。

### 3.2 中循环(一局 2–5 分钟)

一局 = 一次无尽堆叠,直到溢出。玩家的目标-奖励闭环是:
**制造一次连锁 → 堆高度骤降 → 获得喘息空间和高倍分 → 在更空的场地上重新组织。**

连锁既是分数来源,也是**唯一的清场手段**。这一条把「爽」和「活下去」绑成同一个动作,是本作最重要的系统设计决定:玩家不需要在「保命」和「刷分」之间选边,追求高连锁本身就是最优的生存策略。

### 3.3 宏循环(跨局)

- **破本地最高分**(主)与**破最高连锁数**(副,单独记录、单独显示)。
- **可感知的技能成长**:新玩家把块往空处丢,场面越铺越平、越铺越高;熟练玩家会**故意造斜坡**,把不稳定的楔形和多面球当作「触发器」丢在堆顶,让它滚到指定位置。这个差距是掌握感的主要来源。
- 每一局的堆都长得不一样(刚体物理的天然内容量),没有「打完了」。

## 4. 落点控制方案(本作最重要的一个决定)

3D 里落点是 X/Z 平面上的一个点,比 2D 多一个自由度。三个候选:

| 方案 | 玩家在做什么 | 好处 | 代价 | 结论 |
| --- | --- | --- | --- | --- |
| (a) 固定落点 + 容器可旋转 | 转容器,块永远从正上方掉 | 输入只有 1 个自由度;视觉上很酷 | **致命**:旋转容器 collider 会把已堆好的几十个刚体一起推挤,求解器必然爆炸;若改成转相机则重力方向和画面不一致,玩家立刻晕。而且旋转期间整堆都在动,消除判定的接触采样全程失效 | **否决** |
| (b) 拖一个悬空投放指示器,在 X/Z 平面自由定位 | 在一个俯视/斜视的平面上找点 | 真 3D,决策空间最大 | 竖屏斜视相机下,屏幕纵向同时编码了「Z 深度」和「高度」,玩家**根本判断不出深度**;触屏没有精确输入;落点光束要画成 3D 投影才勉强可读;堆变高后前排块会遮挡后排,可读性崩溃 | **否决** |
| (c) 薄井容器,物体只在一个竖直平面内运动(视觉 3D、玩法 2.5D) | 只调 X,和 2D 掉落游戏一样 | 输入 1 个自由度,触屏零学习成本;画面永不自遮挡;**物理求解器稳定性大幅提升**(见下) | 「真 3D」被削弱成「真 3D 渲染 + 平面物理」 | **选它** |

### 4.1 选 (c) 的实现方式(不是「假 3D」,是「约束到平面的真刚体」)

物体仍然是真正的 3D 刚体、真正的 Rapier 凸包 collider、真正的 3D 网格,只是加两条**运动约束**:

```
body.setEnabledTranslations(true, true, false)   // 锁 Z 位移
body.setEnabledRotations(false, false, true)     // 只允许绕 Z 轴自转
```

由此得到的三个好处,每一个都值钱:

1. **稳定性**:接触求解退化成平面问题,同样迭代次数下堆叠抖动显著小于全 3D。本作全部内容就是堆叠,求解器质量是生死线 —— 这也正是选 Rapier 而不是 cannon-es 的理由,这条约束把这个优势再放大一次。
2. **可读性**:所有物体的 Z 都是 0,竖屏里屏幕纵向**只编码高度**,不编码深度。落点是确定的、可预测的。
3. **性能**:自由度砍掉一半,接触点数量下降,在用户已经抱怨过掉帧的前提下这是实打实的预算。

**容器只需要 3 个静态 collider:地板 + 左墙 + 右墙。** 前后墙不需要(Z 已锁),不要建。前方留空,侧后方用半透明玻璃面板做视觉边界。

### 4.2 输入映射

**触屏(主)**

- **在play 区内按下** → 瞄准器立刻横向跳到手指 X 并持续跟随(1:1 映射,不做加速曲线)。手指不需要碰到方块本体 —— 这样手指不会遮挡块和落点。
- **抬起(pointerup)= 投放**。快点一下(按下到抬起 < 120ms)就是「点哪掉哪」,长按拖动就是「边拖边看落点光束」。两者走同一条代码路径。
- `pointercancel` / 指针离开画布 → **取消本次投放**,瞄准器留在原地不投放(防误投)。
- 只接受第一根有效手指,忽略额外触点。
- 容器需要 `touch-none`,禁止页面滚动与缩放。

**键鼠(桌面)**

- 鼠标移动 = 瞄准(不需要按下),**左键单击 = 投放**。
- `←` / `→` / `A` / `D` 按住 = 瞄准器连续横移,速度 6.5 单位/秒,起步有 120ms 加速斜坡(避免点一下动太多)。
- `空格` 或 `↓` = 投放。
- `P` / `ESC` = 暂停。结算页 `R` 或 `空格` = 再来一局(需要一次新的按下事件,见 §13)。

**投放冷却 `dropCooldownMs = 250`**:防止连点双发,也保证玩家至少看到一眼落体。

### 4.3 明确不做的输入

- **不做旋转当前块**。多一个按钮 = 多一层决策 = 多一套触屏布局,而本作的乐趣本来就来自「让物理去决定它怎么躺」。列为 §16 的头号扩展候选。
- **不做 hold / 换块**。见 §11 退化打法 #3。
- 不做多指手势、陀螺仪、双击。

## 5. 相机(晕眩风险控制)

**结论:完全固定的相机。不跟随、不拉远、不环绕、不自转。**

竖井的全部高度(地板到警戒线以上)**永远在画面内**,所以没有任何跟随的必要。相机一动就有晕眩风险,而本作玩家的眼睛需要长时间盯着一个静态参照系去判断「这堆歪了没有」—— 相机动会直接破坏这个判断。

### 5.1 世界尺度与机位

| 项 | 值 |
| --- | --- |
| 单位 | 1 世界单位 ≈ 1 个基础方块边长 / 0.9 |
| 竖井内宽 `ARENA_WIDTH` | **5.4**(= 6 个基础方块并排) |
| 地板平面 | `y = 0`(地板 collider 顶面) |
| 墙高 | `y = 0 → 14`(collider),玻璃面板同高 |
| **警戒线 `DANGER_Y`** | **10.0** |
| 投放平面 `SPAWN_Y` | **12.4** |
| 相机 | `PerspectiveCamera(fov 46, aspect 540/960, near 0.5, far 60)` |
| 相机位置 | `(0, 8.2, 16.5)` |
| 相机朝向 | `lookAt(0, 6.0, 0)` → 俯角约 **7.6°** |

俯角 7.6° 的作用:能看到方块的**顶面**一小条,深度感和堆叠层次立刻成立;再大就开始出现前排遮后排(即使 Z 锁死,物体本身有 0.9 的厚度),再小就完全变成 2D 剪影。**这个角度是「看起来是 3D」和「看得清」的平衡点,调它之前先想清楚。**

### 5.2 取景验算(实现时必须核对)

在 z = 0 平面上,`fov 46°`、距离 16.5 时可见高度 ≈ `2 × 16.5 × tan(23°) ≈ 14.0`,可见宽度 ≈ `14.0 × 0.5625 ≈ 7.9`。

- 宽度 7.9 > 竖井 5.4 ✓,左右各留 1.25 的余量给玻璃墙和辉光。
- 高度 14.0 覆盖 `y ∈ [-0.8, 13.2]`(考虑俯角带来的偏移)✓,地板和投放平面同时在框内。
- **验收要求**:竖井的四个角(`x = ±2.7`,`y = 0` 与 `y = 12.4`)投影后必须落在画布安全区内(距边缘 ≥ 24px)。DPR、HUD 覆盖层都不得侵占这块。

### 5.3 唯一允许的相机运动:冲击回弹

只有一种:消除/重击时的**屏震**,而且是相机位置的**平移**,绝不是旋转(旋转型屏震是晕眩的主要来源)。

| 事件 | 位移幅度 | 时长 | 曲线 |
| --- | --- | --- | --- |
| 重落地(冲量 > `IMPACT_SHAKE_MIN`) | 0.04–0.10 单位(按冲量线性) | 120 ms | 指数衰减 |
| 消除 1 组 | 0.10 单位 | 180 ms | 指数衰减 |
| 连锁第 n 次 | `min(0.10 + 0.03n, 0.28)` 单位 | 180 ms | 指数衰减 |

抖动方向随机取 XY 平面单位向量。衰减结束后**必须硬性归位到基准位置**(不要靠衰减自然趋零 —— 浮点残留会让相机永久偏移几个像素,长局后画面就歪了)。

## 6. 物体类型(造型与颜色**绑定**)

### 6.1 为什么绑定而不是两个独立维度

「造型」和「颜色」是**同一个类型的两种冗余编码**,一一对应,不可拆。理由:

1. 消除规则是「同类型」,如果造型和颜色独立,玩家会立刻产生「到底看哪个?」的歧义,而这个歧义在 3D 里、在小屏上、在物体翻滚的情况下是灾难性的。
2. 冗余编码 = 无障碍。色觉障碍玩家靠轮廓分辨,小屏/低亮度下靠颜色分辨,两条通道互为兜底。
3. 造型同时是**物理性格**:楔形会让东西滑,多面球会滚,长板会搭桥。类型 = 颜色 + 轮廓 + 手感,三位一体才立得住。

### 6.2 类型表(全部凸包,MVP 6 种)

| # | 名称 | 几何(Three) | Rapier collider | 尺寸 | 颜色 | 物理性格 |
| --- | --- | --- | --- | --- | --- | --- |
| 0 | **方块** Cube | `BoxGeometry` | `cuboid(0.45,0.45,0.45)` | 0.9³ | 青 `#3ad6e0` | 最稳,地基 |
| 1 | **长板** Plank | `BoxGeometry` | `cuboid(0.9,0.225,0.45)` | 1.8×0.45×0.9 | 琥珀 `#f2b23a` | 架桥、盖顶,也最容易翘翘板 |
| 2 | **圆木** Log | `CylinderGeometry` 轴转到 X | `cylinder` 轴 X | 长 1.3,r 0.45 | 紫 `#a06cf0` | 侧视是圆角矩形,稳但不吃力 |
| 3 | **楔形** Wedge | 三棱柱(自建 BufferGeometry) | `convexHull` | 底 1.1,高 0.95,厚 0.9 | 绿 `#5fdc7a` | 斜坡制造机,是「主动制造塌方」的工具 |
| 4 | **多面球** Icosa | `IcosahedronGeometry(0.5, 0)` | `convexHull` | r 0.5 | 橙 `#ff8a3d` | **会滚一段再停在某个面上** |
| 5 | **六棱柱** Hex | `CylinderGeometry(0.55,0.55,0.9,6)` 轴 Z | `convexHull` | r 0.55,厚 0.9 | 粉 `#ff6fa8` | 六边形轮廓,能滚一点点,咬合好 |

**#4 用二十面体而不是真球,这是一个刻意的设计决定。** 真球在低摩擦下会永远滚到墙角,让整个类型变成不可控的垃圾;二十面体滚 1–3 下就会停在一个面上 —— 保留了「圆的东西会跑」的戏剧性,同时保证它最终会停在一个玩家能预期的地方。

**全部 collider 必须是凸的。** 不做十字块、L 块、凹形块 —— 凹形需要 compound collider,接触点数量翻倍、稳定性下降、`convexHull` 也不能直接用。这是本作最重要的一条性能/稳定性红线。

### 6.3 质量配平(容易被忽略的稳定性关键)

**逐类型调密度,使所有物体的质量落在 0.55–0.95 之间,任意两类的质量比不超过 2:1。**

刚体求解器在高质量比下会明显抖动:一个很轻的块被压在很重的块下面时,接触冲量会来回震荡。均一密度会让楔形(体积 ≈ 0.47)和圆木(体积 ≈ 0.83)差出 1.8 倍,二十面体更轻。所以密度不是物理真实性问题,是**稳定性旋钮**:

| 类型 | 体积(约) | 密度 | 质量(约) |
| --- | ---: | ---: | ---: |
| Cube | 0.729 | 1.00 | 0.73 |
| Plank | 0.729 | 1.00 | 0.73 |
| Log | 0.827 | 0.90 | 0.74 |
| Wedge | 0.470 | 1.55 | 0.73 |
| Icosa | 0.318 | 2.20 | 0.70 |
| Hex | 0.786 | 0.95 | 0.75 |

目标质量统一在 **0.73 ± 0.03**,质量比 ≈ 1:1。若后续为了手感差异化要拉开质量,**上限是 2:1**,超过就要重新验证堆叠抖动。

### 6.4 类型数随进度的曲线

难度按**本局已投放数 `drops`** 推进(与时间无关)。

| 阶段 | drops | 场上类型数 | 用意 |
| --- | --- | ---: | --- |
| 教学 | 1–8 | **3** | 三种类型下,随手丢也很容易凑成 3 个,**第一次爆炸几乎是必然的** |
| 展开 | 9–24 | **4** | 加入第 4 类,开始需要分区堆放 |
| 压力 | 25–48 | **5** | 场面开始留残渣,连锁的价值凸显 |
| 极限 | 49+ | **6** | 全类型,凑齐靠规划 |

新类型的加入顺序固定:`Cube → Plank → Icosa → Wedge → Log → Hex`。前 3 个先给最稳的两种加一个滚的,让「物理会捣乱」这件事第一时间出现,但只出现一点点。

**类型数上限就是 6,不再往上加。** 7 种以上在 540 宽的屏幕上颜色开始难分辨,而且后期永远凑不齐 = 没有希望 = 玩家提前放弃。

### 6.5 生成权重(偏向场上已有类型)

对每个已激活类型 `t`:

```
base(t)      = 1.0
fieldBias(t) = 1 + BIAS_K * clamp(fieldCount(t), 0, 3) / 3
starve(t)    = (t 在最近 12 次投放中没出现过) ? 2.0 : 1.0
w(t)         = base(t) * fieldBias(t) * starve(t) * typeWeight(t)
```

- `BIAS_K` 默认 **0.8**;当场上物体总数 > 18(拥挤)时提升到 **1.6**。这是本作的**压力阀**:越危险,越容易拿到能救命的类型。它同时是防挫败设计和难度自适应,一石二鸟。
- `typeWeight`:Cube 1.2 / Plank 1.0 / Log 1.0 / Hex 1.0 / Wedge 0.85 / Icosa 0.75。不稳定类型天然少出。
- `drops > 40` 后,Wedge 与 Icosa 的 `typeWeight` 各 ×1.3(混乱度缓慢上升)。这是唯一的外加难度曲线。
- **硬规则:同一类型不得连续生成超过 2 次。** 第 3 次强制从其他类型里重抽。没有这条,「连着来 3 个同类丢一堆」会变成无脑解法。
- 抽样用不重复的加权轮盘,不要用 `while (t === last) retry` 这种可能不终止的写法 —— 直接把被禁类型的权重置 0 后归一化。

## 7. 消除判定规格(接触是抖的,必须做时间滤波)

### 7.1 接触怎么采样

**用 Rapier 自己维护的接触图,不要自己做距离/AABB 判定。**

自己做距离判定必然出错:两个同类块隔着一个薄板,中心距很近,但它们并没有接触 —— 距离判定会把它们判成一组。这是这类玩法最经典的一个 bug。

```
对每个存活 entity e:
  world.contactPairsWith(e.collider, (other) => {
    // 只处理 idA < idB 的一半,避免重复
    // 只处理 type 相同的对
    world.contactPair(e.collider, other, (manifold, flipped) => {
      if (manifold.numSolverContacts() > 0) markPair(a, b)
    })
  })
```

`numSolverContacts() > 0` 表示求解器这一步真的在这对之间施加了约束 = 真接触。比自己判 `manifold.contactDist() < eps` 更可靠。若需要放宽,备用条件是任一接触点 `dist <= CONTACT_EPS = 0.02`。

> ⚠️ **必须在运行时验证的假设**:Rapier 的 island 休眠后,narrow phase 的 contact pair 是否仍然保留。设计上应当保留(collider 仍然重叠),但**如果实测发现休眠体的接触对消失,会导致「堆稳定下来之后反而不消除」这种最恶劣的 bug**。兜底方案二选一:(1) 关掉休眠 `setCanSleep(false)`,代价是 CPU;(2) 一旦某对进入稳定态就把它缓存进持久邻接表,只在其中一方被移除或被唤醒时才重新校验。**实现前先写 10 行 demo 验证这一条。**

### 7.2 时间滤波(防误触发 / 防漏触发)

采样**不是每帧做**,而是每 `MATCH_TICK_MS = 100ms`(每 6 个物理步)做一次。

维护 `Map<pairKey, age>`,`pairKey = min(idA,idB) * 1e6 + max(idA,idB)`:

```
每个 match tick:
  本 tick 采到的对        → age += 1
  已在表中但本 tick 没采到 → miss += 1;若 miss >= 2 则从表中删除,否则保留 age 不变
  age >= CONTACT_STABLE_TICKS(=3) 的对 → 视为「稳定接触边」
```

- **进入需要 3 个 tick(300ms)连续接触**:滤掉落体擦过、弹跳中的瞬时接触。
- **退出需要 2 个 tick(200ms)连续失联**:滤掉稳定堆里 1 帧的接触丢失(求解器把两块推开 0.001 又贴回来)。
- 这个**迟滞(hysteresis)是整套判定的核心**。只做进入门槛会漏触发,只做退出门槛会误触发,两个都要。

### 7.3 连通分量与消除

对所有**稳定接触边**做并查集(union-find),只在同类型之间连边。

```
每个 match tick:
  1. 重建/增量维护并查集
  2. 找出 size >= CLEAR_THRESHOLD(=3) 的分量
  3. 按 size 降序取前 MAX_GROUPS_PER_TICK(=3) 组
  4. 每组:标记 pendingRemoval,同一 tick 内已被标记的 entity 不再进入第二组
  5. 播放消除表现 → 移除刚体 → 结算分数
```

**`CLEAR_THRESHOLD` 恒定为 3,永不随进度变化。** 阈值是玩家学会的第一条规则,改它等于中途改规则,学习成本白付。难度靠类型数和场面复杂度表达,不靠阈值。

被判定为消除的组不需要「静止」条件 —— 300ms 的接触稳定期本身已经排除了乱飞状态,而且塌方过程中的连锁**必须**能在物体仍在运动时触发,否则最爽的那部分就没了。

### 7.4 消除的执行顺序(会被写错的地方)

```
1. 标记 entity.state = 'clearing',立即把它的 collider 设为 sensor 或直接从 world 移除刚体
2. 网格保留 140ms 播放消除动画(scale 1.0 → 1.25 → 0,颜色打到白)
3. 动画结束后:mesh 从 scene 移除、entity 从 map 删除、其相关的所有 pairKey 从接触表清除
```

**刚体必须在第 1 步就移除,不能等动画播完。** 等 140ms 会让上面的堆「悬在空中」再突然掉,塌方的因果关系断掉,玩家会觉得是卡顿。视觉残留和物理消失分离,是这类消除游戏的标准做法。

移除刚体后**立刻把该 entity 的所有引用置空**,并从 `Map<handle, entity>` 中删除。Rapier 的 body 是 WASM 侧对象,removeRigidBody 之后再访问就是 use-after-free。

## 8. 塌方连锁循环(本作的高潮,也是最容易做成死循环的地方)

### 8.1 为什么天然没有死循环风险

**消除不是递归函数,是每 100ms 一次的固定 tick。**

不要写「消除 → 让物理稳定 → 再检查 → 再消除」的递归/while 结构。那种结构一旦出现「消除后立刻又满足条件」就会锁死主线程。本作的结构是:

```
主循环每帧:
  物理步进(固定 1/60,累加器,单帧最多 2 步)
  每 6 步 → 跑一次 match tick(采样 + 判定 + 最多消 3 组)
  渲染
```

消除只是这条流水线上的一个有界步骤。**单个 tick 的工作量有硬上限(3 组),不管场面多疯狂,帧时间都是可预测的。** 剩下的组会在下一个 tick(100ms 后)被处理 —— 它们已经稳定,不会丢。而且这 100ms 的错峰反而让连锁在视觉上一段一段地炸开,比一帧全炸好看得多。

### 8.2 「等多久让物理稳定」

**不等。** 消除后物理照常步进,堆自然塌落。接触滤波的 300ms 进入门槛就是天然的稳定等待期:塌下来的块要连续接触 300ms 才算数,这段时间正好覆盖了自由落体和第一次弹跳。

不需要任何「settle 状态」,不需要状态机分支,不需要暂停输入。**这是本设计里最省代码的一个决定,同时也是手感最好的一个 —— 玩家在塌方期间仍然可以正常投放下一块,连锁和操作是并行的。**

### 8.3 连锁计数

```
onClear():
  now = performance.now()
  if (now - lastClearAt <= CHAIN_WINDOW_MS)  chainIndex += 1
  else                                        chainIndex  = 0
  lastClearAt = now
```

- `CHAIN_WINDOW_MS = 900`。取值理由:一块从警戒线高度落到地板约 1.0 秒,900ms 意味着「塌下来立刻又凑上」算连锁,而「玩家又丢了一块才凑上」通常不算(投放冷却 250ms + 落体时间 ≥ 600ms,刚好卡在窗口外沿)。**这条边界决定了连锁是奖励塌方还是奖励手速,900 是有意偏向塌方的。**
- **同一 tick 内消掉的多组算同一个连锁层级**,不是各自 +1。它们额外吃「同步消除」奖励(见下)。

### 8.4 计分

```
sizeBonus(k) = k=3 → 1.0 | k=4 → 1.3 | k=5 → 1.7 | k>=6 → 2.2
groupScore   = 30 * k * sizeBonus(k)
chainMult    = min(1 + 0.5 * chainIndex, CHAIN_MULT_CAP = 5.0)
syncMult     = (本 tick 消除组数 >= 2) ? 1.5 : 1.0
score       += round(groupScore * chainMult * syncMult)
```

举例:

| 情形 | 计算 | 得分 |
| --- | --- | ---: |
| 单独消 3 个 | 30×3×1.0×1.0×1.0 | 90 |
| 单独消 5 个 | 30×5×1.7×1.0 | 255 |
| 塌方连到第 4 次,消 3 个 | 30×3×1.0×2.5 | 225 |
| 连到第 6 次且同 tick 双组,消 4 个 | 30×4×1.3×3.5×1.5 | 819 |

- **投放本身 0 分。** 不给放置分,否则「无脑乱丢刷分」就成立了(见 §11 #1)。分数只来自消除。
- `chainIndex` 上限保护:计数器仍然累加(HUD 要显示「x9 连锁」这种成就感),但倍率封顶 5.0。封顶是为了防止一次超长连锁直接锁死排行榜、让后续所有局都失去意义。
- **HUD 上的连锁数字是本作最重要的正反馈载体**:每 +1 就放大一次(scale 1.0 → 1.35 → 1.0,140ms),音效基频按 `440 × 1.12^chainIndex` 上行。这个音阶上行是玩家「感觉自己很牛」的主要来源,不能省。

## 9. 溢出判定(不能用瞬时高度)

物体会弹跳、会被挤飞、投放时本来就在警戒线以上。所以判定必须同时满足三个条件。

### 9.1 规则

```
每个 match tick(100ms):
  eligible = 存活 entity 中满足:
      e.hasBeenBelowDanger == true          // 一次性闸门,见下
      && |linvel| < OVERFLOW_VEL_MAX (0.6)  // 排除正在被弹飞的
      && e.body.translation().y > DANGER_Y  // 用重心,不用 AABB 顶
  若 eligible 非空 → overflowMs += 100
  否则             → overflowMs = max(0, overflowMs - 200)   // 回落速度 2 倍
  若 overflowMs >= OVERFLOW_HOLD_MS (1500) → 游戏结束
```

三个条件各自解决一个问题:

- **`hasBeenBelowDanger` 一次性闸门**:每个 entity 在其重心第一次降到 `DANGER_Y` 以下时置 true,之后永不复位。**没有这条,刚投放的块就在警戒线上方,一放就死。** 用「曾经进过场」而不是用「存活时长 > N ms」,因为后者在长距离落体时会误判。
- **`|linvel| < 0.6`**:一块被挤飞冲过警戒线又落回来,不应该算。只有**停在那里**才算。
- **用重心不用 AABB 顶**:一块竖着立起来的长板顶端高出 0.9,不该因为「尖尖露头」就判死。玩家的直觉是「堆到那儿了」,重心才对应这个直觉。

`overflowMs` 的**回落速度是上升速度的 2 倍**:玩家一旦通过消除把高度降下来,压力条要迅速松开,给出明确的「我救回来了」的反馈。惩罚积累慢、消解快,是防挫败的标准做法。

### 9.2 预警表现(零文字)

| `overflowMs` | 表现 |
| --- | --- |
| 0 | 警戒线以 10% 不透明度常驻显示(**从开局第一秒就画出来**,让玩家在它变重要之前就知道它存在) |
| > 0 | 警戒线 300ms 内淡入到 100%,开始 3Hz 脉冲;玻璃墙自下而上泛起红色,强度 = `overflowMs / 1500` |
| ≥ 750 | 脉冲提到 6Hz;画面四周红色暗角(vignette,用一个覆盖在 canvas 上的 CSS 径向渐变实现,零 GPU 成本);低频心跳音每 700ms 一次 |
| ≥ 1200 | 心跳提到每 400ms;越界的那几个 entity 本体轮廓描红(材质 emissive 拉高),**明确告诉玩家是哪几块要了他的命** |
| 归零 | 全部特效 250ms 内淡出 |

最后那条「描红越界物体」是**归因反馈**,不可省。没有它,玩家死了只知道「太高了」,不知道「是那块滚到边上支起来的板害的」,下一局不会改进。

### 9.3 逃逸兜底

正常情况下不会发生(有墙、有速度上限、投放期开 CCD),但必须有:

```
每个 match tick:若 e.y < -5 或 |e.x| > 20 → 静默移除该 entity(不加分、不算消除、不播特效)
```

## 11. 退化打法与反制

| # | 退化打法 | 反制 |
| --- | --- | --- |
| 1 | 无脑乱丢刷分 | **投放本身 0 分**,分数只来自消除。乱丢只会更快堆满 |
| 2 | 全部丢在正中间堆一根柱子 | 柱子超过 4–5 层必然歪倒(重心窄、`restitution` 低但摩擦有限),自动散开。这是物理自带的反制,不需要额外规则 |
| 3 | 「攒牌」:等到好用的类型再放 | **不做 hold / skip / 换块**。当前块必须投放,无法跳过。这是唯一有效也最省代码的反制 |
| 4 | 靠生成偏向自动过关(游戏自己帮你凑 3 个) | `BIAS_K` 只影响概率,不保证相邻;`MAX_SAME_TYPE_RUN = 2` 保证不会连着送 3 个同类;而且消除要求**互相接触**,接触只能靠玩家摆出来 |
| 5 | 只往两个墙角堆(靠墙最稳) | 这是**正当技巧,不封杀** —— 靠墙确实更稳,这正是熟练度的体现。但墙角堆到 `DANGER_Y` 一样会溢出,而且靠墙的堆很难触发大塌方,分数天花板低。策略间的取舍是真实的(自我决定论里的「自主」:多条都可行的路) |
| 6 | 卡缝穿模 / 投放到已有物体内部导致爆炸弹飞 | **投放前做重叠检查**:用当前块的形状在出生位置做一次 `world.intersectionsWith`(或对 ghost 建一个临时 sensor),若与任何 entity 重叠 → 禁止投放,ghost 变红并播放一声短促的拒绝音。这条必须有,否则堆到顶时会出现物体互相穿透后弹飞的灾难 |
| 7 | 抖动导致误消除(两块隔着缝被判成接触) | §7.2 的 3-tick 进入门槛 + 只认 `numSolverContacts() > 0` |
| 8 | 抖动导致漏消除(明明堆稳了却不炸) | §7.2 的 2-tick 迟滞退出;以及 §7.1 的休眠接触图风险验证 |
| 9 | 靠塌方无限连锁刷分 | `CHAIN_MULT_CAP = 5.0`;而且每次连锁都在**降低堆的高度**,连锁越长场面越空,后续越难继续连 —— 系统自带负反馈 |
| 10 | 切后台挂机 / 暂停当作思考时间 | `visibilitychange` 失焦即暂停(物理不步进)。暂停时**用一层不透明遮罩盖住 canvas**,防止把暂停当无限观察时间。恢复需要一次新的按下 |
| 11 | 卡在「场上全是残渣、永远凑不齐」的死局 | `BIAS_K` 压力阀(拥挤时 1.6)+ 饥饿保底(12 次没出现就翻倍权重)。两条都是概率性的救济,不是保证 —— 保证会消解紧张感 |
| 12 | 结算页点击穿透成为新一局的第一次投放 | 结算与新一局之间**必须等待一次新的 pointerdown**;新一局开始后 300ms 内忽略投放输入 |
| 13 | 疯狂连点投放,让多个块在空中重叠 | `dropCooldownMs = 250` + #6 的重叠检查(上一块还没离开出生区就禁止投放) |

## 12. 单局结构与持久化

### 12.1 模式

**只有一个无尽模式,不做模式选择,不做难度档菜单。**

neon-strike 和 fruit-slasher 做多模式是对的,因为它们的难度是「敌人多快多硬」这种可以外部调节的连续量。本作的难度**是玩家自己堆出来的** —— 场面越乱越难,而场面完全由玩家的每一次投放决定。再叠一个难度档,只会让配平矩阵翻三倍,而且新玩家在开局根本无法判断自己属于哪一档,这个选择是假的。**难度用系统内生表达,不用菜单表达。**

### 12.2 结算页

| 显示项 | 说明 |
| --- | --- |
| **本局得分** | 大号,居中 |
| **最高连锁 ×N** | 与得分同级显示。这是玩家最有情绪的一个数字 |
| 消除组数 / 消除方块数 | 小字 |
| 投放数 | 小字,配合上面两项能算出「效率」 |
| 历史最高分 / 是否新纪录 | 新纪录时金色描边 + 一次性庆祝粒子 + 五音上行琶音 |
| 「再来一局」按钮 | 需要一次新的按下(§11 #12) |

**结算页背景保留最后那一帧的堆**(冻结物理、保持渲染),让玩家看到「我是怎么死的」。这比任何数字都有归因价值。越界的物体保持描红。

### 12.3 storage.ts(照抄 neon-strike 的读写模式)

```
KEYS = {
  best:   'tumble-stack-best',     // 数字字符串,首页卡片可能会读,格式不要改
  stats:  'tumble-stack-stats',    // JSON
  muted:  'game-box-muted',        // 全站共用,复用现有键
  volume: 'game-box-volume',       // 全站共用,复用现有键
}

stats = { best: number, bestChain: number, totalClears: number, runs: number }
```

- `read` / `write` 必须包 `try/catch`(隐私模式下 localStorage 会抛),且判 `typeof localStorage === 'undefined'`(SSR)。
- 解析失败 / 字段类型不对 → 全部回退到 0,不影响开局。
- **`game-box-muted` / `game-box-volume` 复用全站键**,与 neon-strike 保持一致,静音设置跨游戏生效。

## 13. 状态流程

### 13.1 加载(本作独有,因为有 WASM)

```
菜单出现之前必须完成:await RAPIER.init()
```

- `RAPIER.init()` 的 Promise **缓存在模块作用域**,重复进出游戏页只 init 一次。
- 加载期显示一个极简进度态(GameShell 已有「加载中…」的位置)。**预算:首次 1.5 秒内,二次进入 0 秒。**
- 若 `RAPIER.init()` reject(WASM 被 CSP 拦、老浏览器不支持):显示一行降级文案「你的浏览器不支持本游戏所需的物理引擎」,不要白屏、不要无限转圈。
- **加载期间用户可能已经点了返回。** `destroy()` 必须能在 init 尚未 resolve 时被调用,并用 `disposed` 标志阻止后续的场景构建。这是本作最容易漏的一个竞态。

### 13.2 菜单

- 标题、最高分、最高连锁、一个「开始」按钮。
- 背景是**活的封面**:一个已经在跑的物理场景,每 1.2 秒自动往里丢一块,堆满一定高度后整体淡出重置。它同时是最好的教学素材 —— 玩家在点开始之前就已经看懂了「东西会掉会堆」。
- 单击开始立即进入,不做二次确认。

### 13.3 游戏中

- HUD(DOM 覆盖层,不用 3D 文字):左上得分、左上小字最高分、右上**下一块**预览(一个小的 3D 缩略图或纯色圆点 + 轮廓图标)、居中偏上的连锁计数(仅 `chainIndex > 0` 时出现)、右上角暂停按钮。
- 暂停:`P` / `ESC` / 按钮 / 失焦。暂停时物理不步进、不透明遮罩覆盖 canvas。

### 13.4 结算 → 重开

**重开必须重置**:得分、连锁计数与 `lastClearAt`、`drops`、`overflowMs`、当前块与下一块、生成器的最近类型队列与连续同类计数、**接触对表(pairKey → age/miss)**、并查集、粒子池(全部粒子归池)、屏震偏移与相机基准位置、所有 `setTimeout`、音频节点。

**Rapier world 的处理**:重开时**销毁旧 world 并新建一个**(`world.free()` 后 `new RAPIER.World(gravity)`),不要试图逐个 `removeRigidBody` 复用 —— 复用会残留接触图和 island 状态,是「第二局手感和第一局不一样」这类玄学 bug 的温床。新建 world 的成本可以忽略。

保留:最高分、最高连锁、静音/音量设置。

## 14. 上手引导(前 10 秒,零文字教程)

**开局的场面是预置的,不是空的。**

1. **开局竖井里已经躺着 4 块**:正中偏左有 **2 个互相接触的同类块**(固定为 Cube),右侧散着 2 个另外类型的块作为对照。
2. **第 1 块手上拿的一定是 Cube**(与那两个同类)。
3. 那两个已接触的 Cube 从第一帧起就在**呼吸辉光**(§10.2 的 `pairGlow`)。玩家还没做任何操作,就已经看到「这两个之间有某种关系」。
4. 玩家随手往中间一丢 → 大概率碰到那两块 → **爆炸 + 加分 + 屏震**。**规则在第一次操作就教完了**,一个字没写。
5. 若玩家第一块丢歪了没碰上:场上现在是「2 个 Cube + 1 个 Cube 在别处」,第 2 块仍然强制给 Cube(前 2 次投放的类型是脚本化的),他还有第二次机会。**前 2 块脚本化,第 3 块起进入 §6.5 的随机生成。**
6. **落点光束 + 落点椭圆**从第一帧就在,教「它会掉到这儿」。
7. **若开局 2.5 秒无输入**:瞄准器自动左右滑动 1.2 单位一个来回(1.0 秒),演示「这东西可以移动」。第一次按下立即中断。
8. **警戒线从第一秒起以 10% 不透明度画着**,在它变重要之前玩家就知道它存在。

**全局唯一的文字**是 HUD 上的数字、暂停/再来一局按钮上的字。菜单页额外允许一行:「三个同类碰到一起就炸」。

## 15. 反馈设计(产品层定「该有什么」,具体表现由 ART.md 定)

每个操作在 **0.5 秒内**必须有可读反馈。

| 事件 | 视觉 | 音效 | 震动/时间 |
| --- | --- | --- | --- |
| 瞄准移动 | ghost 跟手;落点光束与椭圆实时更新 | 无(高频事件,加音会烦) | — |
| 投放 | ghost 瞬间实体化;出生点一圈 0.3 单位的白色扩散环,180ms | 短促气音(白噪 40ms,低通扫频) | — |
| 落地(按冲量分级) | 接触点喷 4–10 个粒子;被撞的块挤压 0.94 倍回弹 120ms | 闷响,基频按冲量 90–160Hz,时长 60ms | 屏震 0.04–0.10 单位 / 120ms(仅冲量超阈值) |
| **两块同类稳定接触** | **两块 emissive 同步呼吸,0.5Hz,±15%** | 首次接上时一声很轻的「叮」(1200Hz,30ms,音量 0.25) | — |
| 消除 1 组 | 各块 scale 1.0→1.25→0(140ms)并打白;每块喷 12 个该类型颜色的粒子(初速径向 3–6,受重力,寿命 500–800ms);地面一圈冲击波环 | 明亮的合成音,基频 `440 × 1.12^chain` | 屏震 0.10 单位 / 180ms |
| 连锁 +1 | HUD 连锁数字 scale 1.0→1.35→1.0(140ms),颜色随层级从白 → 黄 → 橙 → 红 | 音高按层级上行(同上) | 屏震幅度递增至 0.28 封顶 |
| 同 tick 多组 | 额外一次全屏 60ms 的轻微白闪(透明度 ≤ 0.12,**不要更强,会闪眼**) | 叠加一个低八度和声 | — |
| 加分 | 从消除中心用世界坐标投影出 DOM 浮动数字,上飘 40px,700ms 淡出 | — | — |
| 投放被拒(重叠/冷却) | ghost 变红闪一下(120ms) | 短促下行「哔」(220→180Hz,80ms) | — |
| 溢出预警 | 见 §9.2 | 心跳低频音 | — |
| 游戏结束 | 全场物理冻结;越界物体描红;画面去饱和 400ms;结算页从下方滑入 250ms | 下行三音 | 屏震 0.2 单位 / 260ms |
| 新纪录 | 结算页金色描边 + 庆祝粒子 | 五音上行琶音 | — |

**反馈可读性底线(最重要的一条)**:玩家死的时候必须知道**是哪几块害的**。所以结算时保留最后一帧的堆、保持越界物体描红。没有这一条,玩家会觉得「莫名其妙就结束了」,下一局不会有任何改进,宏循环直接断掉。

**粒子必须池化**:`PARTICLE_POOL = 240`,单个 `BufferGeometry` + `Points`,每帧只更新属性数组、不做任何分配。一次 6 连锁会同时触发 200+ 粒子,如果每次爆炸都 new 一个粒子系统,GC 尖峰会直接掉帧 —— 而掉帧是用户已经在抱怨的问题。

## 16. 性能预算

| 项 | 预算 | 做法 |
| --- | --- | --- |
| 刚体数 | 峰值 ≤ 45,硬上限 64 | 竖井小,溢出会先触发 |
| Draw call | ≤ 55 | 每类型共享 1 个 `BufferGeometry` + 1 个 `MeshLambertMaterial`(共 6+6);墙/地板/线各 1;粒子 1。**若实测超预算,改用每类型一个 `InstancedMesh`,可压到 ~12,但会增加约 60 行管理代码 —— 先测再改,不要预先优化** |
| 光照 | 1 个 `DirectionalLight` + 1 个 `AmbientLight`,**`shadowMap` 关闭** | 阴影贴图是本作性价比最低的开销 |
| 后处理 | **无** | 暗角用 CSS 径向渐变覆盖层实现 |
| 抗锯齿 | `devicePixelRatio > 1.5` 时 `antialias: false` | |
| `pixelRatio` | `min(devicePixelRatio, 2)`;若连续 60 帧平均帧时间 > 22ms,自动降到 1.25 并**不再回升**(避免来回抖动) | |
| 物理步进 | 单帧最多 2 步 | 累加器 + 丢弃超额时间 |
| 判定 | 每 100ms 一次,单 tick 最多消 3 组 | §7 / §8 |
| 材质/贴图 | **零纹理**,纯色 + 光照 | 与仓库「运行时生成、不依赖外部资源」的约定一致 |
| Bundle | Three tree-shake 后 gzip ~150KB;`rapier3d-compat` 的 wasm ~1MB(gzip 后 ~400KB) | **只在 `/tumble-stack` 路由动态加载**,首页与另外三款零影响。这是本作最大的一笔体积开销,必须在提案里认账 |

**性能降级顺序(实测掉帧时按序执行)**:`pixelRatio` → `numSolverIterations` 8→6→4 → 粒子池 240→120 → 改 `InstancedMesh`。

## 17. WebGL / WASM 资源回收(playtest_critic 检查清单)

这是本作**最高优先级的技术风险**,而且比 shadowcast 更重 —— 多了一整套 WASM 生命周期。漏回收的表现是「反复进出游戏页十几次后页面变白」或「浏览器标签内存持续上涨直到崩溃」,开发期极难注意到。

`startGame` 返回的对象在 `destroy()` 时**必须逐条完成**,顺序不可随意调换:

### 17.1 循环与输入

1. `cancelAnimationFrame(rafHandle)`,handle 置空;设 `disposed = true`,让循环体第一行就 `return`。
2. **`disposed` 必须同时阻断所有 `await` 之后的续行**:`RAPIER.init()`、动态 `import('three')` 的 `.then` 里都要先查 `disposed`。加载期返回首页是真实路径。
3. 移除**全部** DOM 监听:`pointerdown` / `pointermove` / `pointerup` / `pointercancel` / `pointerleave`、`keydown` / `keyup`、`visibilitychange`、`resize`、`contextmenu`。**注册时用具名函数保存引用,不要用匿名箭头函数。**
4. 清掉所有 `setTimeout` / `setInterval`(消除动画延时、心跳音、结算滑入、开局演示、投放冷却)。用一个 `timers: Set<number>` 统一登记与清理。

### 17.2 Rapier(WASM 侧,漏了不会报错但会泄漏 wasm 堆)

5. 停止步进后,`world.free()`。**这一步之后不得再访问任何 `RigidBody` / `Collider` 的 JS 句柄** —— 它们指向已释放的 wasm 内存,访问会是 use-after-free(表现可能是静默的错误数据,也可能是硬崩)。
6. 清空 `Map<colliderHandle, entity>` 与所有 entity 上的 `body` / `collider` 引用(置 `null`)。
7. 若创建了 `EventQueue`,`eventQueue.free()`。
8. 若使用了 `RAPIER.QueryPipeline` / `Ray` / 临时 shape 等显式对象,逐个 `free()`。**每帧创建的 `Ray`(落点检测)必须复用同一个实例,不要每帧 new** —— 每帧 new 一个 wasm 对象是最隐蔽的泄漏来源。
9. **`RAPIER.init()` 的模块级 Promise 不要清空**。wasm 模块实例本来就该跨挂载复用,清空只会让第二次进入重新下载解析。这是唯一一处「故意不释放」,要在代码注释里写明,否则会被后来者当成 bug 修掉。
10. 游戏中途移除刚体一律用 `world.removeRigidBody(body)`(它会连带移除该 body 的 colliders),**不要**再单独对其 collider 调 `free()`。

### 17.3 Three(GPU 侧)

11. 遍历 scene,收集所有 `geometry` 与 `material` 到 **`Set` 去重后**统一 `dispose()`。**同一类型的所有方块共享同一个 geometry/material 实例**,既不能漏、也不能重复 dispose。
12. 材质上挂的任何 `map` / `alphaMap` / `envMap`(本作应为零)也要 `texture.dispose()`。
13. 粒子系统的 `BufferGeometry` 与 `PointsMaterial` 单独 dispose。
14. `scene.clear()`,并把 `scene` / `camera` 引用置空。
15. **`renderer.dispose()` → `renderer.forceContextLoss()` → `renderer.domElement.remove()` → 引用置空。三步缺一不可**,只调 `dispose()` 不会释放 WebGL context。

### 17.4 音频与 DOM

16. 所有还在响的 `OscillatorNode.stop()` + `disconnect()`,`GainNode.disconnect()`,最后 `audioContext.close()`。
17. 移除 HUD 覆盖层的所有 DOM 节点与它们身上的监听(HUD 是 DOM,不是 canvas,容易被忘)。

### 17.5 幂等

18. `destroy()` **必须幂等**:重复调用不抛错、不重复 `free()`(重复 `world.free()` 会崩)。用一个 `disposed` 标志在函数第一行短路。`PhaserCanvas` 的卸载路径存在异步竞态,可能调用两次。
19. `destroy(removeCanvas?)` 的参数**忽略即可**(为兼容 `Phaser.Game` 的签名),但签名必须接受它。

### 17.6 验收方法

- 在 `/tumble-stack` 与首页之间**连续来回 20 次**:Console 不得出现 `Too many active WebGL contexts` 或 `WebGL context lost`。
- DevTools 内存快照:`WebGLRenderer` 实例数为 0,`Detached HTMLCanvasElement` 数为 0。
- 20 次来回前后对比 `performance.memory.usedJSHeapSize` 与 wasm 内存(`WebAssembly.Memory.buffer.byteLength`),后者**不得单调增长**。
- 在加载动画还在转的时候点返回,重复 10 次,不得报错。
- 一局玩到 200 次消除后,`Map<handle, entity>` 的 size 应等于场上存活物体数(泄漏检查)。

## 18. 对项目契约的改动

`src/games/types.ts` 当前写死返回 `Phaser.Game`,需要放宽为结构化类型:

```ts
export type GameInstance = { destroy: (removeCanvas?: boolean) => void };
export type GameModule = { startGame: (parent: HTMLElement) => GameInstance };
```

- `Phaser.Game` 天然满足这个结构,**现有三款游戏一行都不用改**。
- `PhaserCanvas.tsx` 里的 `destroy(true)` 调用点保持不变。
- **本作不与 Phaser 共存。** 不在同一页跑两个渲染循环。HUD 用覆盖在 canvas 上的 DOM 实现。
- 新增依赖:`three`、`@dimforge/rapier3d-compat`。**这是本作唯一的外部依赖增量,必须在拍板时明确认账。** `rapier3d-compat`(而非 `rapier3d`)是必须的:它把 wasm 内联成 base64,不需要配 Turbopack 的 wasm loader,也不需要处理 `.wasm` 静态资源路径 —— 代价是包体略大、需要 `await init()`。**在这个项目里,省掉打包配置的价值远大于那点体积。**

## 19. MVP 验收标准

### 功能

- 触屏「按下-拖动-抬起投放」与鼠标「移动-点击投放」手感一致;键盘可完成全部操作(移动 + 投放 + 暂停 + 重开)。
- 竖井四角在 540×960 下完整可见,不被 HUD 遮挡。
- 所有刚体的 Z 位移与 X/Y 旋转确实被锁死(打印任意 body 的 `translation().z` 恒为 0,四元数的 x/y 分量恒为 0)。
- 3 个同类接触必消除;隔着一块异类的两块**不得**被判成接触。
- 消除后塌方能正确触发连锁,连锁计数与倍率符合 §8.3/§8.4。
- **连续消除 500 次不掉帧、不卡死、不出现「消不掉的残留组」。**
- 溢出判定不会因为「刚投放的块在警戒线上方」而误杀(`hasBeenBelowDanger` 闸门生效)。
- 投放重叠检查生效:堆到顶时不出现物体互相穿透后弹飞。
- 暂停 / 失焦 / 恢复 / 结算 / 重开不残留定时器、监听器、接触表、粒子或旧刚体。
- §17 的 20 次进出测试与 wasm 内存检查全部通过。
- `pnpm lint` 与 `pnpm build` 通过。

### 体验(「手感对了」的判据)

- **块落地是「砸实」的,不是「弹」的,也不是「飘」的。** 这是第一优先级,不对就不要往下做。
- 瞄准跟手,落点光束指哪落哪,没有可感知的偏差。
- 玩家在消除发生前 0.5 秒就能预感到「要炸了」(靠 `pairGlow` 和落点预判)。
- 连锁的音高上行 + 数字放大 + 屏震递增三者同步,能明确制造「越来越爽」的爬升感。
- 玩家死后能说出「是那块 XX 害的」。
- 新玩家在**不看任何文字**的情况下,10 秒内完成第一次消除。
- 中低端手机(4 年前的中端安卓)稳定 55fps 以上,峰值 45 个刚体时不掉到 40 以下。

**这超出「几百行」的常规单款预算约 3 倍,必须认账。** 增量集中在三处,每一处都不是可以随手砍的:

1. **Rapier 接触判定与迟滞(~120 行)** —— 这是本作的规则本体,砍了就没有游戏。
2. **Three + Rapier 的手工生命周期管理(~110 行,分散在 render/physics/index)** —— 没有 Phaser 的 `destroy(true)` 一把梭,这部分是纯粹的税。
3. **DOM HUD(~190 行)** —— 因为不能用 Phaser 的场景系统,菜单/暂停/结算都要手写。

### 削减版(MVP−,约 1000 行)

如果要压到接近常规体量,按以下顺序砍:

1. **砍菜单页的「活封面」物理场景**(-60 行)—— 换成静态标题。代价:失去一个免费的教学窗口。
2. **砍类型数从 6 到 4**(Cube / Plank / Icosa / Wedge,-50 行几何与配平)—— 代价:后期变化度下降,但**核心循环完全不受影响**。这是性价比最高的一刀。
3. **砍浮动分数与暗角**(-50 行)—— 代价:反馈层次变薄。
4. **砍下一块预览**(-40 行)—— 代价明显:失去规划维度,决策深度下降一档。**建议最后才砍。**
5. **砍暂停功能,只保留失焦自动暂停**(-50 行)。
6. **HUD 用最朴素的几个 div,不做动画**(-80 行)—— 代价:连锁的爽感损失很大,**不推荐**。

**绝对不能砍的**:接触迟滞(§7.2)、`hasBeenBelowDanger` 闸门(§9.1)、投放重叠检查(§11 #6)、粒子池化(§15)、§17 的全部回收步骤。这五条每一条被砍掉都会产生「build 通过但游戏是错的」那类问题。

### 明确不做的东西(范围控制)

- **不做 X/Z 平面自由落点**(理由见 §4)。物理约束到 XY 平面。
- **不做容器旋转**。
- **不做当前块的旋转操作**。头号扩展候选,但不在 MVP。
- **不做 hold / skip / 换块**(理由见 §11 #3)。
- **不做凹形 / compound collider**。全部凸包。
- **不做真球**,用二十面体(理由见 §6.2)。
- **不做阴影贴图、后处理、SSAO、反射、辉光 bloom**。emissive 直接调材质,不走后处理。用户已在抱怨掉帧。
- **不做外部 3D 模型 / GLTF / 纹理贴图**。全部程序化几何 + 纯色。
- **不做多模式、难度菜单、复活道具、连击保护、限时模式**。
- **不做倒计时压力**。压力来自堆的高度,不来自时钟。
- **不做联网排行、成就、每日挑战**。
- **不做相机跟随、拉远、环绕**(理由见 §5)。

## 21. 后续可选扩展(不属于 MVP)

按性价比排序:

1. **旋转当前块**(空格/双击 = 顺时针 90°)。增量极小(~30 行),决策深度立刻上一个台阶。**如果 MVP 做完还有预算,第一个加它。**
2. **三车道深度**(`DEPTH_LANES = 3`):把锁死的 Z 放开成 3 个离散车道,上/下键切换,渲染上有明确的前后错位。这才是「真 3D 玩法」的正确加法 —— 离散车道保留了落点的可读性,同时引入深度维度。增量约 80 行(相机需要略微加大俯角,车道要有清晰的视觉区分)。
3. **特殊块**:炸弹块(落地消掉半径内所有物体)、万能块(可与任意类型连通)。各约 40 行,是最便宜的内容量扩展。
4. **每日种子**:用日期做生成器种子,全球同一套出块序列,无需服务端。
5. **重力翻转 / 倾斜事件**:每 30 次投放,竖井整体倾斜 8° 持续 10 秒。戏剧性极强,但会打破所有稳定的堆 —— 需要仔细验证求解器在倾斜过程中的表现,风险中等。

扩展优先级原则:**优先增加「玩家能预谋的东西」,而不是增加随机性或内容量。** 旋转和车道都符合这条;特殊块次之;倾斜事件是纯随机性,优先级最低。
